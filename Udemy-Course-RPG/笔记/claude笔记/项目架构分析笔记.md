# 类银河恶魔城 RPG 游戏项目架构分析笔记

## 一、项目概览

这是一个基于 **Unity 6** 的 2D 横版动作 RPG 游戏 Demo，风格上融合了**类银河恶魔城（Metroidvania）**的探索要素与**动作 RPG** 的角色成长系统。项目采用模块化架构，系统间通过接口和事件解耦，大量使用 **ScriptableObject** 做数据驱动。

---

## 四、核心架构：实体-组件模式（Entity-Component）

### 4.1 设计理念

项目采用 **"一个基类 + 多个功能组件"** 的模式。`Entity` 是所有游戏实体的基类，提供物理碰撞检测、移动、翻转、击退等基础功能。具体的功能（生命、战斗、状态、掉落、视觉/听觉效果）通过**独立组件**附加，职责高度单一。

### 4.2 Entity 基类 (`Scripts/Entity/Entity.cs`)

```
继承链：MonoBehaviour → Entity → Player / Enemy
```

**核心职责：**
- **组件缓存**：在 `Awake()` 中自动获取 Animator、Rigidbody2D、Collider2D、Entity_SFX
- **状态机驱动**：持有 `StateMachine` 实例，`Update()` 中调用 `stateMachine.UpdateActiveState()`
- **物理碰撞检测**：使用 Raycast2D 检测地面和墙壁（`groundDetected`、`wallDetected`）
- **水平翻转**：`HandleFlip()` 通过 `transform.Rotate(0,180,0)` 实现角色翻转，并触发 `OnFlipped` 事件
- **击退系统**：`ReciveKnockback()` 使用协程实现受击位移
- **减速系统**：`SlowDownEntity()` 支持叠加/覆盖逻辑

### 4.3 Entity 功能组件一览

| 组件 | 职责 | 接口实现 |
|------|------|---------|
| `Entity_Health` | 生命值管理、受伤/治疗/死亡逻辑、击退计算、生命回复 | IDamagable |
| `Entity_Combat` | 攻击检测（OverlapCircleAll）、伤害计算、命中反馈 | — |
| `Entity_Stats` | 属性系统封装，提供 GetAttackData/GetArmorMitigation 等 | — |
| `Entity_StatusHandler` | 元素状态效果（冰冻减速、火焰灼烧、雷电感电） | — |
| `Entity_DropManager` | 死亡/开启时的物品掉落（基于稀有度权重随机） | — |
| `Entity_VFX` | 受击闪白、残影特效、元素状态变色 | — |
| `Entity_SFX` | 音效播放 | — |

**关键设计：**
- 组件之间通过 `GetComponent<T>()` 互相获取引用，不依赖 Inspector 拖拽
- `Entity_Health` 同时实现 `IDamagable` 接口，使得任何实体（包括宝箱、技能物体）都可以被攻击系统统一处理

```
    │       │       ├── Player_BasicAttackState
    │       │       ├── Player_JumpAttackState
    │       │       ├── Player_DeadState
    │       │       ├── Player_CounterAttackState
    │       │       ├── Player_SwordThrowState
    │       │       └── Player_DomainExpansionState
    │       │
    │       └── EnemyState（敌人状态基类）
    │               ├── Enemy_IdleState
    │               ├── Enemy_MoveState
    │               ├── Enemy_BattleState

    │               ├── Enemy_DeadState
    │               └── Enemy_StunnedState
    │               └── (子类扩展：ArcherElf/Mage/Reaper/Slime 专用状态)
```

### 5.2 StateMachine 核心

```csharp
// Scripts/StateMachine/StateMachine.cs
public class StateMachine
{
    public EntityState currentSate { get; private set; }
    public bool canChangeState = true;

    public void Initialize(EntityState startState)  // Enter 初始状态
    public void ChangeState(EntityState newState)    // Exit → Enter
    public void UpdateActiveState()                   // 每帧调用 currentSate.Update()
}
```

**核心流程：**
1. `Initialize(startState)` → 调用 `startState.Enter()`
2. 每帧 `UpdateActiveState()` → 调用 `currentSate.Update()`
3. `ChangeState(newState)` → `旧状态.Exit()` → 赋值 → `新状态.Enter()`
4. `canChangeState` 锁：防止在状态切换期间再次切换

### 5.3 EntityState 基类设计

```csharp
public abstract class EntityState
{
    protected StateMachine stateMachine;
    protected string animBoolName;    // 对应的动画参数
    protected Animator anim;
    protected Rigidbody2D rb;
    protected Entity_Stats stats;
    protected float stateTimer;        // 状态计时器
    protected bool triggerCalled;      // 动画事件触发器

    public virtual void Enter() { /* 设置动画 bool */ }
    public virtual void Update() { /* stateTimer 递减，更新动画参数 */ }
    public virtual void Exit()  { /* 清除动画 bool */ }
    public void AnimationTrigger() { triggerCalled = true; }
}
```

**设计亮点：**
- **动画与状态强制绑定**：每个状态必须提供一个 `animBoolName`，Enter/Exit 自动设置
- **triggerCalled 机制**：配合 Animation Event，实现在动画播放到特定帧时通知状态切换（主要用于攻击状态→通过 `triggerCalled` 判断攻击动画是否播完）
- **stateTimer**：通用计时器，每帧自动递减，子状态可直接使用

### 5.4 PlayerState 中间层

在 `EntityState` 基础上增加了 Player 特有引用（Player本体、Input、SkillManager）：

```csharp
public abstract class PlayerState : EntityState
{
    protected Player player;
    protected PlayerInputSet input;
    protected Player_SkillManager skillManager;
    // 在 Update 中统一处理 Dash 和 Ultimate 技能的输入检测
}
```

**关键设计：Dash 和 DomainExpansion 的输入在 PlayerState 层统一处理**，这样所有玩家状态都能响应这两个全局技能输入，无需每个子状态重复检测。

### 5.5 EnemyState 中间层

```csharp
public class EnemyState : EntityState
{
    protected Enemy enemy;
    // 在 UpdateAnimationParameters 中处理战斗移动速度的动画参数同步
}
```

### 5.6 状态切换示例：玩家普攻连招

`Player_BasicAttackState` 支持三段连招：

1. **Enter** → 检查时间重置 combo 索引 → 设置 anim integer → 施加攻击位移
2. **Update** → 检测再次按下攻击键（QueueNextAttack）→ 等待 `triggerCalled`（动画事件触发）
3. **HandleStateExit** → 如果有排队攻击 → 延迟一帧再 ChangeState 到自身（实现连招衔接）；否则 → 回 idle
4. **Exit** → comboIndex++，记录攻击时间用于 combo 重置判断

## 六、属性系统（Stat System）

### 6.1 设计理念

属性系统采用 **"基础值 + 修饰器列表"** 的模式，支持多来源的临时/永久属性修改，并通过**脏标记（dirty flag）**进行值的惰性计算。

### 6.2 Stat 核心类

```csharp
[Serializable]
public class Stat
{
    [SerializeField] private float baseValue;
    [SerializeField] private List<StatModifier> modifiers;
    private bool needToCaculate = true;   // 脏标记
    private float finalValue;             // 缓存值

    public float GetValue()
    {
        if (needToCaculate)
        {
            finalValue = baseValue + modifiers.Sum(m => m.value);
            needToCaculate = false;
        }
        return finalValue;
    }

    public void AddModifier(float value, string source) { /* 添加并标记脏 */ }
    public void RemoveModifier(string source) { /* 按来源移除并标记脏 */ }
    public void SetBaseValue(float value) { baseValue = value; }
}

[Serializable]
public class StatModifier
{
    public float value;
    public string source;  // 修饰器来源标识（物品ID、Buff源等）
}
```

**设计亮点：**
- **来源追踪**：每个修饰器带 `source` 字符串，移除时按来源精确删除，防止不同来源互相干扰
- **脏标记优化**：频繁读取属性值时无需反复计算
- **Serializable**：可直接在 Inspector 面板中编辑和调试

### 6.3 属性分组

属性被组织成四个分组（都是 `[Serializable]` 类，内嵌在 `Entity_Stats` 中）：

| 分组 | 包含属性 |
|------|---------|
| `Stat_ResourcesGroup` | maxHealth, healthRegen |
| `Stat_OffenseGroup` | damage, critPower, critChance, armorReduction, attackSpeed, fireDamage, iceDamage, lightningDamage |
| `Stat_DefenseGroup` | armor, evasion, fireRes, iceRes, lightningRes |
| `Stat_MajorGroup` | strength, agility, intelligence, vitality |

### 6.4 Entity_Stats 核心方法

```csharp
// 伤害计算
public AttackData GetAttackData(DamageScaleData scaleData)
public float GetPhyiscalDamage(out bool isCrit, float scaleFactor)
public float GetElementDamage(out ElementType element, float scaleFactor)

// 防御计算
public float GetArmorMitigation(float armorReduction)   // 护甲减伤公式: armor/(armor+100)
public float GetElementalResistance(ElementType element) // 抗性上限75%
public float GetEvasion()                               // 闪避上限70%

// 主属性加成
public float GetBaseDamage() => damage + strength       // 力量加攻击
public float GetCritChance() => critChance + agility*0.3// 敏捷加暴击率
public float GetCritPower()  => critPower + strength*0.5// 力量加爆伤
public float GetMaxHealth()  => maxHealth + vitality*5  // 体质加血量
public float GetBaseArmor()  => armor + vitality        // 体质加护甲
```

### 6.5 元素伤害选择逻辑

`GetElementDamage()` 自动选择玩家最高的元素伤害类型作为本次攻击的元素，并在总伤害中加入其他元素的 50% 加成——确保堆多元素属性仍然有收益。

### 6.6 Player_Stats 扩展

```csharp
public class Player_Stats : Entity_Stats
{
    // Buff系统：防止同来源Buff叠加
    public bool CanApplyBuffOf(string source)
    public void ApplyBuff(BuffEffectData[] buffs, float duration, string source)
}
```

Buff 本质上是通过 `AddModifier/RemoveModifier` 实现的临时属性修改，利用协程在 duration 后自动移除。

## 七、战斗系统

### 7.1 伤害流程

```
攻击者（Entity_Combat.PerformAttack()）
  │
  ├─ OverlapCircleAll 检测目标
  │
  ├─ 获取 IDamagable 接口
  │
  ├─ Entity_Stats.GetAttackData(scaleData) → AttackData
  │     ├─ physicalDamage（含暴击判定）
  │     ├─ elementDamage（自动选择最高元素）
  │     └─ ElementalEffectData（冰冻/灼烧/感电参数）
  │
  ├─ damagable.TakeDamage(...)
  │     ├─ 闪避判定
  │     ├─ 护甲减伤: armorMitigation = effectiveArmor/(effectiveArmor+100)，上限85%
  │     ├─ 元素抗性减免，上限75%
  │     ├─ 受伤反馈（受击闪白VFX + 击退）
  │     └─ 死亡检测
  │
  └─ Entity_StatusHandler.ApplyStatusEffect(element, effectData)
        ├─ Ice(Cold): 减速 + 蓝色闪烁VFX
        ├─ Fire(Burn): DOT灼烧（每秒2跳）+ 红色闪烁VFX
        └─ Lightning(Shock): 感电充能，满层触发雷击 + 黄色闪烁VFX
```

### 7.2 伤害缩放数据（DamageScaleData）

每个技能、每次攻击都可配置独立的 `DamageScaleData`：

```csharp
[Serializable]
public class DamageScaleData
{
    public float phsycal = 1;       // 物理伤害倍率
    public float elemental = 1;     // 元素伤害倍率
    public float chillDuration;
    public float chillSlowMultiplier;
    public float burnDuration;
    public float burnDamageScale;
    public float shockDuration;
    public float shockDamageScale;
    public float shockCharge;
}
```

## 八、技能系统（Skill System）

### 8.1 设计架构

技能系统分为两层：

```
Skill_Base（技能逻辑层）              SkillObject_Base（技能物体层）
    ├── Skill_Dash                      ├── SkillObject_Sword
    ├── Skill_Shard                     ├── SkillObject_SwordSpin
    ├── Skill_SwordThrow                ├── SkillObject_SwordBounce
    ├── Skill_TimeEcho                  ├── SkillObject_SwordPeirce
    └── Skill_DomainExpansion           ├── SkillObject_Shard
                                        ├── SkillObject_Health
                                        ├── SkillObject_DomainExpansion
                                        └── SkillObject_TimeEcho
```

- **Skill_Base**（逻辑层）：挂载在 Player GameObject 上，管理冷却、解锁状态、UI 交互
- **SkillObject_Base**（物体层）：实际在场景中生成的技能预制体（飞剑、碎片等），负责碰撞检测、寻敌、伤害

### 8.2 Skill_Base 核心设计

```csharp
public class Skill_Base : MonoBehaviour
{
    protected SkillType skillType;
    protected SkillUpgradeType upgradeType;  // 当前解锁的升级版本
    protected float cooldown;
    private float lastTimeUsed;

    public virtual bool CanUseSkill()  // 检查是否解锁 && 冷却
    public void SetSkillOnCooldown()   // 设置冷却 + 更新UI
    public void SetSkillUpgrade(Skill_DataSO data) // 从SO数据应用升级
}
```

**技能升级机制**：每个技能有多级升级类型（枚举 `SkillUpgradeType`），通过 `Unlocked(upgradeType)` 判断是否拥有特定升级，不同升级改变技能行为。

### 8.3 Player_SkillManager

管理所有技能的集合体，提供统一接口：

```csharp
public class Player_SkillManager : MonoBehaviour
{
    public Skill_Dash dash;
    public Skill_Shard shard;
    public Skill_SwordThrow swordThrow;
    public Skill_TimeEcho timeEcho;
    public Skill_DomainExpansion domainExpansion;

    public void ReduceAllSkillCooldownBy(float amount)
    public Skill_Base GetSkillByType(SkillType type)
}
```

### 8.4 技能类型

| 技能 | 描述 | 升级方向 |
|------|------|---------|
| Dash | 冲刺，短暂无敌 | 起/终点生成残影分身、释放碎片 |
| Shard(TimeShard) | 时间碎片飞弹 | 自动追踪、多重施法、传送、血量回溯 |
| SwordThrow | 投掷飞剑 | 旋转、穿透、弹射 |
| TimeEcho | 时间残影（分身重放动作） | 单次/多次攻击、复制概率、治疗/净化/冷却光环 |
| DomainExpansion | 展开领域（终极技） | 减速领域、自动残影、自动碎片 |

### 8.5 技能与属性系统的结合

技能的伤害数据来自 `DamageScaleData`，通过 `Entity_Stats.GetAttackData(scaleData)` 动态计算出实际伤害——这意味着同一个技能在不同角色属性下伤害不同，实现了装备/属性驱动的技能伤害。

## 九、背包与物品系统

### 9.1 架构

```
Inventory_Base（背包基类，实现 ISaveable）
```

### 9.2 Inventory_Item

物品实例类（非 MonoBehaviour），包含：

```csharp
[Serializable]
public class Inventory_Item
{
    public string itemId;       // 唯一标识（GUID）
```

### 9.3 ItemDataSO 物品数据体系

```
ItemDataSO（基类 ScriptableObject）
    ├── ConsumableDataSO（消耗品）
    └── EquipmentDataSO（装备，含 ItemModifier[]）
```

物品支持：名称、图标、类型、堆叠上限、价格、稀有度（影响掉落权重）、制作配方、特殊效果。

### 9.4 物品效果系统（ItemEffect）

```
ItemEffect_DataSO（抽象基类 ScriptableObject）
    ├── ItemEffect_Heal                 # 治疗
    ├── ItemEffect_Buff                 # 属性Buff
    ├── ItemEffect_GrantSkillPoints     # 增加技能点
    ├── ItemEffect_PortalScroll         # 创建传送门
    ├── ItemEffect_HealOnDoingDamage    # 伤害吸血
    ├── ItemEffect_IceBlastOnTakingDamage # 受击冰爆
    └── ItemEffect_RefundAllSkills      # 重置所有技能
```

使用 **策略模式**：每个效果是一个独立的 ScriptableObject 子类，`ExecuteEffect()` 执行具体逻辑。消耗品和装备都可附加效果。

### 9.5 装备系统

装备栏通过 `Inventory_EquipmentSlot` 管理：
- 每个槽位指定接受的 `ItemType`
- 装备时：`AddModifiers()` 修改属性 → `AddItemEffect()` 注册被动
- 卸下时：`RemoveModifiers()` → `RemoveItemEffecct()`
- 换装时保存/恢复血量百分比，避免血量上限变化导致的意外死亡

### 9.6 掉落系统

`Entity_DropManager.RollDrops()` 算法：
1. 遍历掉落表，按 `itemRarity` 计算掉率（稀有度越低越容易掉）
2. 通过掉率判定的物品进入候选列表
3. 按稀有度降序排列，依次加入最终掉落，直到总稀有度超过上限

## 十、存档系统

### 10.1 架构

```
SaveManager（单例，场景入口）
    ├── FileDataHandler（文件读写 + XOR 加密）
    ├── GameData（序列化数据容器）
    └── ISaveable 接口 → 所有需要存档的组件实现
```

### 10.2 ISaveable 接口

```csharp
public interface ISaveable
{
    void LoadData(GameData data);
    void SaveData(ref GameData data);
}
```

实现了该接口的组件：
- `GameManager` — 最后场景、玩家位置
- `Inventory_Player` — 物品、装备、金币
- `Player_QuestManager` — 活跃/完成任务
- `Object_Checkpoint` — 已激活的检查点
- `Object_Portal` — 场景中的传送门状态
- `UI_SkillTree` — 技能点、已解锁技能
- 等等

### 10.3 存档流程

1. **启动时**：`SaveManager.Start()` → `FileDataHandler.LoadData()` → 遍历所有 ISaveable 调用 `LoadData()`
2. **保存时**：遍历所有 ISaveable 调用 `SaveData(ref data)` → `FileDataHandler.SaveData(data)`
3. **自动保存**：`OnApplicationQuit()`、场景切换时

### 10.4 数据容器

`GameData` 使用 `SerializableDictionary<TKey, TValue>`（自定义可序列化字典）存储所有游戏状态。`SerializableDictionary` 通过 `ISerializationCallbackReceiver` 接口，在序列化时将字典拆成 key/value 两个 List，反序列化时重组。

### 10.5 加密

`FileDataHandler` 使用 XOR 加密（密钥："laizeyou"）对 JSON 字符串做简单的字节异或——这是基础防护，不是真正意义上的安全加密。

## 十六、设计模式总结

| 设计模式 | 应用位置 | 说明 |
|---------|---------|------|
| **状态模式** | StateMachine + EntityState 体系 | 角色的每个行为是一个状态对象 |
| **策略模式** | ItemEffect_DataSO 子类 | 每种物品效果是独立策略 |
| **组件模式** | Entity + 各功能组件 | 实体功能通过组合而非继承实现 |
| **观察者模式** | C# event/Action | OnFlipped, OnHealthUpdate, OnTakingDamage 等 |
| **单例模式** | Player, GameManager, SaveManager, UI | 全局唯一访问点 |
| **模板方法模式** | EntityState.Enter/Update/Exit | 定义状态生命周期框架，子类填充 |
| **数据驱动** | ScriptableObject | 物品、技能、属性、对话、任务全用 SO |
| **接口隔离** | IDamagable, IInteractable, ISaveable, ICounterable | 小而精的接口 |
| **脏标记模式** | Stat.needToCaculate | 属性值惰性计算 |
| **对象池** | (未实现，但残影/碎片等频繁生成物目前用 Instantiate) | 可优化点 |

## 十七、优点与值得学习的设计

### 17.1 实体-组件拆分：小而美的典范

这个项目最值得学习的地方，就是把一个"角色"拆成了 `Entity`（基类壳子）+ 若干个单一职责的组件。

```
Entity.cs           → 只有物理、移动、翻转
Entity_Health.cs    → 只有血量、伤害、死亡
Entity_Combat.cs    → 只有攻击判定、命中
Entity_Stats.cs     → 只有属性系统
Entity_StatusHandler→ 只有元素异常状态
Entity_DropManager  → 只有掉落逻辑
Entity_VFX.cs       → 只有视觉特效
Entity_SFX.cs       → 只有音效
```

**为什么好？**

- 每个文件 150-200 行，打开就能看完，不用来回翻
- 改战斗逻辑不会误伤血条显示，改属性计算不会影响掉落
- Player 和 Enemy 直接复用同一套组件，几乎是零成本共享
- 如果要加"护盾系统"，只需要加一个新组件，不改任何已有代码

**与你可能见过的反面做法对比：** 很多新手会把所有逻辑塞进一个 `Player.cs`，几千行下来翻到崩溃。这个项目的做法就是解药。

### 17.2 状态机三层继承：恰到好处的抽象层次

```
StateMachine（纯逻辑，32行） 
  → EntityState（抽象基类，提供 anim/rb/stats/timer）
    → PlayerState（中间层，注入 input/skillManager，统一处理Dash输入）
      → 具体状态
    → EnemyState（中间层，注入 enemy 引用，处理战斗动画速度）
      → 具体状态
```

**为什么好？**

- `StateMachine` 本身只有 32 行，没有多余概念，就是 Enter/Exit/Update
- `EntityState` 把 anim、rb、stats 这些所有状态都需要的引用缓存好，子类直接用
- **PlayerState 中间层是点睛之笔**：Dash 和 DomainExpansion 作为"任何状态都能触发的全局技能"，输入检测写在这一层，13 个 Player 状态一步到位全部继承——不用每个状态里重复写 `if (dash键按下) ...`

**状态切换的关键机制 `triggerCalled`**：攻击动画播到特定帧时通过 Animation Event 设置 `triggerCalled = true`，状态在 Update 中检测到后执行退出逻辑。这比用固定秒数等待动画结束更可靠——动画速度变化时不会出错。

### 17.3 Stat 属性系统：用脏标记代替每帧计算

```csharp
// 每次 AddModifier / RemoveModifier → needToCaculate = true
// GetValue() 只在 needToCaculate == true 时才真正计算
// 其余时候直接返回缓存值
```

一帧内可能读取几十次属性值（伤害计算、UI 刷新、移动速度等），但属性本身不会每帧变化。这个简单的惰性求值避免了大量无效运算。

**StatModifier 的 source 追踪**也值得注意——装备卸下时按 `itemId` 精确移除自己的加成，不会误删同名 Buff。这是一个很容易被忽略但一旦出 bug 非常难排查的细节。

### 17.4 ScriptableObject 数据驱动：策划友好的设计

物品、技能升级、属性模板、对话、任务——全部用 `CreateAssetMenu` 生成 SO 资产文件。好处：

- **策划不需要碰代码**，在 Inspector 里填数值就能创建新物品/新技能升级
- **不会因为改 Excel 导入出错**，数据直接在 Unity 编辑器内管理
- **Git 友好**：SO 文件是 `.asset` 文本格式，可以 diff 查看数值变更
- **`OnValidate()` 自动生成 saveId**：`AssetDatabase.AssetPathToGUID(path)` 保证了每个 SO 有唯一 ID，存档/数据库查找不会出问题

### 17.5 伤害计算流程：单一入口，数据驱动

```
Entity_Combat.PerformAttack()
  → Entity_Stats.GetAttackData(damageScale)
    → GetPhyiscalDamage(out isCrit)  // 含暴击判定
    → GetElementDamage(out element)  // 自动选最高元素
    → new ElementalEffectData(...)   // 计算灼烧/冰冻/感电参数
  → damagable.TakeDamage(...)        // 含闪避、护甲减伤、抗性减免
  → statusHandler.ApplyStatusEffect()// 施加元素异常
```

整个伤害链从一个入口进去，所有计算集中在一处。如果要调整伤害公式，只需要改 `Entity_Stats` 里的几个方法，不会散落在几十个文件中。

### 17.6 存档系统：接口驱动，零侵入

`ISaveable` 接口只有两个方法，任何需要存档的组件自行实现。`SaveManager` 启动时用 `FindObjectsByType<MonoBehaviour>().OfType<ISaveable>()` 自动发现所有需要存档的组件——**新增存档数据不需要在 SaveManager 里注册任何东西**。

### 17.7 UI 的输入焦点管理：简单可靠

打开 UI 面板时的逻辑：

```csharp
void StopPlayerControls(bool stopControls)
{
    if (stopControls) input.Player.Disable();
    else              input.Player.Enable();
}
```

`InputActionMap` 整体 Enable/Disable，不逐一处理每个 Action——UI 面板打开时玩家输入全部禁用，关闭时全部恢复。代码量极少但完全满足需求。

### 17.8 装备系统的血量保护

换装备时，血量上限变化（比如卸下加体质的装备），项目做了这个处理：

```csharp
float savedHealthPercent = player.health.GetHealthPercent();
// ... 装备/卸下操作 ...
player.health.SetHealthToPercent(savedHealthPercent);
```

如果不保存百分比，卸下装备会让最大血量突然降低 → 可能导致角色"假死"或血量溢出。这种边界情况处理体现了一定的工程素养。

## 十八、缺点与改进建议

### 18.1 组件间依赖用 GetComponent：隐式耦合的隐患

```csharp
// Entity_Health.cs
entity = GetComponent<Entity>();
entityStats = GetComponent<Entity_Stats>();
entityVfx = GetComponent<Entity_VFX>();
dropManager = GetComponent<Entity_DropManager>();
```

**问题：** 每个组件都在 `Awake()` 中自己 `GetComponent`，组件之间形成了一个**隐式依赖网**。如果一个 GameObject 上漏挂了 `Entity_VFX`，`Entity_Health` 不会报错（因为 `GetComponent` 返回 null），但受击时就没有视觉反馈——静默失败。

**改进方案：**

```csharp
// 方案A：Awake 中做防御性检查（简单直接）
private void Awake()
{
    entityStats = GetComponent<Entity_Stats>();
    if (entityStats == null) 
        Debug.LogError($"{name} 缺少 Entity_Stats 组件！");
}

// 方案B：用 [RequireComponent] 属性让 Unity 自动保证依赖存在
[RequireComponent(typeof(Entity_Stats))]
[RequireComponent(typeof(Entity_VFX))]
public class Entity_Health : MonoBehaviour { ... }

// 方案C：通过初始化方法显式注入（更规范的 DI）
public void Initialize(Entity_Stats stats, Entity_VFX vfx) { ... }
```

对于个人项目，方案 A + B 组合足够；商业项目考虑方案 C。

### 18.2 没有对象池：GC 压力的定时炸弹

残影效果（`Entity_VFX.CreateImage()`）、技能物体（飞剑、碎片）、命中特效——全部用 `Instantiate()` 创建，用 `Destroy()` 销毁。这些对象在战斗中高频生成（Dash 残影、Shard 碎片、受击特效在同一帧可能创建 10+ 个），GC Alloc 会导致间歇性卡顿。

**具体影响：** Entity_VFX 的 ImageEcho 协程每 0.05 秒 Instantiate 一次残影，Dash 期间连续创建 5 个，战斗密集时 GC 触发会造成明显的帧率波动。移动平台（手机/Switch）上这个问题会被放大。

**改进方案：**

```csharp
// 简单对象池示例
public class SimplePool<T> where T : Component
{
    private Queue<T> pool = new Queue<T>();
    private T prefab;
    
    public T Get()
    {
        T obj = pool.Count > 0 ? pool.Dequeue() : Object.Instantiate(prefab);
        obj.gameObject.SetActive(true);
        return obj;
    }
    
    public void Return(T obj)
    {
        obj.gameObject.SetActive(false);
        pool.Enqueue(obj);
    }
}
```

优先池化：残影物体 → 技能投射物 → 命中 VFX → 掉落物品

### 18.3 技能系统职责边界模糊

当前一个技能的完整逻辑分散在三处：
- `Skill_Base` 子类（如 `Skill_Dash`）：只负责"起/终点生成 clone/shard"
- `PlayerState` 子类（如 `Player_DashState`）：负责 Dash 的完整流程（重力、无敌帧、速度）
- `SkillObject_Base` 子类：负责飞行物体的碰撞和伤害

一个技能的"业务逻辑"被拆得很散。比如想理解 Dash 技能到底做了什么，你需要同时看三个文件。而且 `SkillUpgradeType` 枚举有 30+ 个值，每加一个新升级就要在枚举、Skill_Base 子类的 switch、SkillObject 子类三处修改。

**改进方案：** 可以考虑让技能类本身成为一个更完整的"技能控制器"，状态机只负责调用 `skill.Execute()` 和 `skill.IsFinished()`，具体行为由技能类内部编排：

```csharp
public abstract class Skill_Base : MonoBehaviour
{
    public virtual void OnEnter() { }
    public virtual void OnUpdate() { }
    public virtual void OnExit() { }
    public virtual bool IsFinished() { return false; }
}
```

这样看一个技能只需要打开一个文件。

### 18.4 静态事件耦合：扩展的暗礁

```csharp
// Player.cs
public static Action OnPlayerDeath;

// Enemy.cs
Player.OnPlayerDeath += HandlePlayerDeath;
```

`static event` 看起来简洁，但有三个隐患：
1. **内存泄漏**：如果 Enemy 被销毁时没取消订阅（还好这个项目在 `OnDisable` 中做了），会导致 GC 无法回收
2. **场景切换问题**：`static` 事件跨场景存在，新场景加载后旧引用可能还存在
3. **难以调试**：无法直观看到"谁在监听这个事件"，出问题时只能全局搜索

**改进方案：** 引入一个轻量级的 EventBus/MessageBus：

```csharp
public static class EventBus
{
    private static Dictionary<Type, Delegate> events;
    
    public static void Subscribe<T>(Action<T> handler) where T : struct { ... }
    public static void Unsubscribe<T>(Action<T> handler) where T : struct { ... }
    public static void Publish<T>(T eventData) where T : struct { ... }
}

// 使用
EventBus.Subscribe<PlayerDeathEvent>(OnPlayerDeath);
EventBus.Publish(new PlayerDeathEvent());
```

或者至少把 `static event` 集中到一个 `GameEvents` 静态类中，方便全局查看。

### 18.5 GameData 膨胀风险

```csharp
public class GameData
{
    public SerializableDictionary<string, int> inventory;
    public SerializableDictionary<string, int> storageItems;
    public SerializableDictionary<string, int> storageMaterials;
    public SerializableDictionary<string, ItemType> equipedItems;
    public SerializableDictionary<string, bool> skillTreeUI;
    public SerializableDictionary<SkillType, SkillUpgradeType> skillUpgrades;
    public SerializableDictionary<string, bool> unlockedCheckpoints;
    public SerializableDictionary<string, Vector3> inScenePortals;
    public SerializableDictionary<string, bool> completedQuests;
    public SerializableDictionary<string, int> activeQuests;
    // ... 还有更多
}
```

所有存档数据堆在一个类里。**目前没问题，但随着功能增加会变成上帝类**。每加一个新系统就要在 GameData 中加一个字段 → GameData 越来越臃肿 → 序列化/反序列化越来越慢 → 存档文件越来越大。

**改进方案：** 让各系统管理自己的存档数据段：

```csharp
// 各系统用 partial 或组合
public class GameData
{
    public InventorySaveData inventoryData;
    public SkillTreeSaveData skillTreeData;
    public QuestSaveData questData;
    // ...
}
```

### 18.6 物品效果系统缺少数据绑定

`ItemEffect_Heal.ExecuteEffect()` 中直接写 `FindAnyObjectByType<Player>()`：

```csharp
public class ItemEffect_Heal : ItemEffect_DataSO
{
    public override void ExecuteEffect()
    {
        Player player = FindAnyObjectByType<Player>(); // ← 运行时查找，脆弱
        float healAmount = player.stats.GetMaxHealth() * healPercent;
        player.health.IncreaseHealth(healAmount);
    }
}
```

**问题：** SO 本身不应该依赖场景中的对象查找。这是 SO 设计中的一个常见误区——SO 应该是纯数据 + 纯逻辑，不应该 `FindAnyObjectByType`。

**改进方案：** 由调用方传入上下文：

```csharp
public class ItemEffect_DataSO : ScriptableObject
{
    public virtual void ExecuteEffect(Player player) { }
}

// 调用时
itemEffect.ExecuteEffect(player);
```

好在 `ItemEffect_Buff` 已经部分意识到了这个问题（在 `CanBeUsed` 中接收 `player` 参数），但没有统一。

### 18.7 代码清洁度问题

通读整个项目代码发现的常见问题：

- **大量被注释掉的旧代码块**：`Entity_Combat.cs`、`Player_QuestManager.cs` 中有整段的注释代码（几十到上百行），做版本对比应该用 git 而不是注释
- **中英混杂日志**：`Debug.Log("On Cooldown")` / `Debug.Log("检测到 collider: " + target.name)`，统一用一种语言
- **拼写错误分散在各处**：`dutation`、`encrpyData`、`Caculate`、`orginal`、`eletrcifyVfx`、`ChracaterUI`、`upagradeData`、`Trink`... 变量/方法/文件夹名中有大量拼写错误。虽然不影响运行，但会让后续维护者困惑
- **Enemy 基类中残留 Debug 代码**：`Enemy.BattleState` 在 Enter 时无条件输出 "������"，可能是中文乱码

### 18.8 缺少单元测试

整个项目没有任何测试代码。对于属性系统（Stat）、伤害计算、掉落算法这些**纯逻辑**模块，单元测试的 ROI 极高——不需要运行游戏就能验证公式正确性。

## 十九、给你的实践建议

### 19.1 做新项目时直接复用的东西

| 可复用部分 | 复用方式 |
|-----------|---------|
| `Stat` + `StatModifier` 属性系统 | 直接拷贝，改命名空间即可 |
| `StateMachine` 核心（32行） | 直接拷贝，它是通用的 |
| `EntityState` → `PlayerState` 三层模板 | 作为新项目的状态机脚手架 |
| `ISaveable` + `SerializableDictionary` | 存档方案的蓝本 |
| `Entity_Health` 的伤害公式 | 作为战斗系统的起点参考 |
| ScriptableObject 数据驱动的思路 | 指导思想，不必拷贝代码 |

### 19.2 做新项目时建议改进的地方

| 问题 | 改进方向 |
|------|---------|
| GetComponent 隐式依赖 | 用 `[RequireComponent]` + Awake 断言 |
| 无对象池 | 项目中期引入，先池化高频对象 |
| 技能逻辑分散 | 让 Skill_Base 做更多编排，状态只做简单调度 |
| static event 耦合 | 用 EventBus 或用 UnityEvent 替代 |
| GameData 膨胀 | 按系统拆成子结构体 |
| SO 中 FindAnyObjectByType | 由调用方传入上下文参数 |
| 无测试 | 至少对 Stat、伤害公式、掉落算法写测试 |
| 中文注释和拼写错误 | 新项目注意代码规范，IDE 开拼写检查 |

### 19.3 给学习路径的建议

这个项目覆盖了一个商业游戏的大部分系统。如果你在学习，建议按以下顺序理解和复现：

1. **先搭骨架**：StateMachine → Entity → Player/Enemy → 一个可移动、可跳跃的角色
2. **再加战斗**：Entity_Health + Entity_Combat + Entity_Stats → 能攻击、能受伤
3. **然后装备成长**：Inventory + Stat 修饰器 → 装备能改属性
4. **接着技能**：Skill_Base + Player_SkillManager → Dash 和投掷飞剑
5. **最后持久化**：SaveManager + ISaveable → 存档读档

不要试图一开始就建所有系统——这项目的作者也是一层层加出来的（从 Enemy 中残留的大量注释代码能看出来迭代痕迹）。

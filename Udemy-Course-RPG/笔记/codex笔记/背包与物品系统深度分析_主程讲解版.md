# 背包与物品系统深度分析_主程讲解版

> 分析对象：`Udemy-Course-RPG` 的背包、物品、装备、仓库、商店、锻造、掉落和快捷栏系统  
> 推荐阅读顺序：先看第 2、3、4 节建立全局图，再看第 6、7 节理解 UI 和场景物体，最后看第 10、11 节排坑。

## 1. 这个系统为什么难懂？

背包与物品系统难，不是因为某个算法复杂，而是因为它横跨了很多层：

```text
ScriptableObject 物品配置
  -> Inventory_Item 运行时物品实例
  -> Inventory_Base / Player / Storage / Merchant 容器逻辑
  -> UI_ItemSlot / UI_Inventory / UI_Storage / UI_Merchant / UI_Craft 显示与点击
  -> Object_ItemPickup / Object_Chest / Object_Merchant / Object_Blacksmith 场景交互
  -> Entity_Stats / Entity_Combat / Entity_Health 装备属性和特殊效果
  -> SaveManager / GameData 存档恢复
```

你会觉得它难，是正常的。它不像技能系统那样一条“输入 -> 释放 -> 生成技能物体”的链路比较直；背包系统更像一个物流仓库：同一件物品可能来自怪物掉落、宝箱、商店、任务奖励，也可能进入背包、仓库、材料仓库、装备栏、快捷栏，还可能被消耗、出售、锻造或存档。

这个项目的核心设计可以概括成一句话：

**物品数据用 `ItemDataSO` 配，运行时用 `Inventory_Item` 包一层，所有容器都继承 `Inventory_Base`，UI 不存真实数据，只订阅背包变化并把 List 映射到 Slot。**

这是理解整个系统的钥匙。

## 3. 系统分层：至少要从 5 个视角看

用户特别提到 UI 和逻辑物体，这两个视角必须讲。但只讲这两个还不够，因为本系统至少有五层：

| 层级 | 代表类 | 解决的问题 |
| --- | --- | --- |
| 数据配置层 | `ItemDataSO`, `EquipmentDataSO`, `ConsumableDataSO`, `ItemListDataSO` | 物品是什么，价格、图标、类型、掉落率、配方、效果是什么 |
| 运行时逻辑层 | `Inventory_Item`, `Inventory_Base`, `Inventory_Player`, `Inventory_Storage`, `Inventory_Merchant` | 物品现在在哪个容器里，堆叠多少，能不能添加、使用、装备、转移、买卖 |
| UI 视图层 | `UI_ItemSlot`, `UI_Inventory`, `UI_Storage`, `UI_Merchant`, `UI_Craft`, `UI_InGame` | 怎么显示、点击后调用哪个逻辑、Tooltip 怎么展示 |
| 场景物体层 | `Object_ItemPickup`, `Object_Chest`, `Object_Merchant`, `Object_Blacksmith`, `Entity_DropManager` | 世界里的物体如何掉落、拾取、打开商店/仓库/锻造 |
| 跨系统接入层 | `Entity_Stats`, `Stat`, `ItemEffect_DataSO`, `SaveManager`, `GameData` | 装备如何改属性，特殊效果如何订阅事件，存档如何恢复 |

这个系统真正的设计思路是：**UI 和场景物体都不直接改属性，不直接操作存档，它们只调用背包逻辑；背包逻辑改完数据后发 `OnInventoryChange`，UI 再刷新。**

这些字段可以分成四类：

你可以把 `ItemDataSO` 理解成“物品图纸”。比如小血瓶这个资产写着：

- `itemName: Small Health potion`

- `maxStackSize: 5`

代码证据：`Assets/Data/Item data/Consumable items data/Consumable data - Small Health potion.asset:19`

它本身不是玩家背包里的那瓶药，只是“这种药的定义”。

### 4.2 EquipmentDataSO 只比普通物品多 modifiers

`ItemModifier` 很简单：

比如 Wooden Sword：

- `itemType: 1`，对应 `Weapon`

这说明装备本身不写“装备时怎么加属性”。装备只配置“加哪些属性”。真正加属性发生在 `Inventory_Item.AddModifiers()`：`Assets/Scripts/InventorySystem/Inventory_Item.cs:30`

### 4.3 ConsumableDataSO 目前只是类型标记

`ConsumableDataSO` 继承 `ItemDataSO`，但没有新增字段：`Assets/Scripts/Data/ItemData/ConsumableDataSO.cs:4`

```csharp
public class ConsumableDataSO : ItemDataSO
{
}
```

你可能会问：既然没字段，为什么还要建子类？

这是为了编辑器创建菜单和未来扩展。现在消耗品的具体效果放在 `ItemEffect_DataSO` 里，而不是放在 `ConsumableDataSO` 里。这样“回血药”“传送卷轴”“技能点书”“洗点书”都能共用同一个消耗品数据结构，只是挂不同的 effect。

### 4.4 ItemType 决定物品去哪、能做什么

`ItemType` 定义在 `Assets/Scripts/Data/ItemType.cs:3`：

```csharp

{
    Material,
    Weapon,
    Armor,
    Trink,
    Consumable

```

这个 enum 很关键，它至少被用于四个地方：

| 场景 | 用法 |
| --- | --- |
| 拾取 | `Material` 不进玩家背包，直接进 `storage.materialStash` |
| 装备 | `Weapon / Armor / Trink` 匹配装备槽 |

| 快捷栏 | `UI_InGame` 只筛选 `Consumable` 做快捷栏候选 |

```csharp
}
```

这个设计会让新手困惑：为什么我捡了材料，背包列表里看不到？答案是它不在 `Inventory_Player.itemList`，而在 `Inventory_Storage.materialStash`。

### 4.5 ItemListDataSO 是“数据库”和“列表”

`ItemListDataSO` 有两个用途：

1. 做全物品数据库，给存档通过 `saveId` 找回物品 SO。
2. 做某个系统的物品列表，比如商店货池、可锻造武器列表、怪物掉落表。

代码位置：`Assets/Scripts/Data/ItemData/ItemListDataSO.cs:5`

```csharp

{
    return itemList.FirstOrDefault(item => item != null && item.saveId == saveId);
}
```

`ITEM DATA BASE.asset` 是存档用数据库，里面列了所有物品：`Assets/Data/Item data/ITEM DATA BASE.asset:15`

`List of items - Merchant's item list.asset` 是商店货池：`Assets/Data/Item data/List of items - Merchant's item list.asset:15`

`List of items - Weapon to craft.asset` 是锻造列表：`Assets/Data/Item data/List of items - Weapon to craft.asset:15`

这也是 Unity 项目很常见的做法：同一个 `ItemListDataSO` 类，不同 asset 表示不同业务列表。

## 5. 运行时逻辑层：Inventory_Item 才是背包里的“那一件”

### 5.1 为什么需要 Inventory_Item？

`ItemDataSO` 是图纸，而 `Inventory_Item` 是运行时实例：`Assets/Scripts/InventorySystem/Inventory_Item.cs:6`

构造函数：

```csharp
public Inventory_Item(ItemDataSO itemData)
{
    this.itemData = itemData;
    itemEffect = itemData.itemEffect;
    buyPrice = itemData.itemPrice;
    sellPrice = itemData.itemPrice * .35f;
    modifiers = EquitmentData()?.modifiers;
    itemId = itemData.itemName + " - " + Guid.NewGuid();
}
```

为什么要包一层？

因为背包里的“物品实例”有一些 SO 不应该保存的数据：

| 运行时字段 | 为什么不能放 SO |
| --- | --- |
| `stackSize` | 每个格子堆叠数不同 |
| `itemId` | 每件装备要有唯一来源，用来精确移除属性 modifier |
| `buyPrice / sellPrice` | 运行时交易价格，可按商店规则缓存 |
| `modifiers` | 装备时要快速读取 |
| `itemEffect` | 使用/装备时执行或订阅 |

最关键的是 `itemId`。装备加属性时，不只是 `AddModifier(+4)`，而是：

```csharp
statToModify.AddModifier(modifier.value, itemId);
```

代码位置：`Assets/Scripts/InventorySystem/Inventory_Item.cs:30`

卸下装备时：

```csharp
statToModify.RemoveModifier(itemId);
```

代码位置：`Assets/Scripts/InventorySystem/Inventory_Item.cs:39`

这就是“来源追踪”设计。没有 `itemId`，你只能按数值删 modifier，两个戒指都加 15 暴击时就分不清该删哪一个。

### 5.2 Inventory_Base 是所有容器的共同能力

`Inventory_Base` 是玩家背包、仓库、商人背包的基类：`Assets/Scripts/InventorySystem/Inventory_Base.cs:6`

核心字段：

```csharp
public event Action OnInventoryChange;
public int maxInventorySize = 10;
public List<Inventory_Item> itemList = new List<Inventory_Item>();
```

这三个字段很重要：

- `itemList` 是真实数据。
- `maxInventorySize` 限制格子数。
- `OnInventoryChange` 是 UI 刷新的信号。

它提供了这些基础操作：

| 方法 | 作用 |
| --- | --- |
| `CanAddItem()` | 判断能不能加入，允许堆叠或有空位 |
| `FindStackable()` | 找同类且未满堆叠的格子 |
| `AddItem()` | 有可堆叠就加 stack，否则新增格子 |
| `RemoveOneItem()` | 减一层堆叠，没了就移除整格 |
| `RemoveFullStack()` | 移除整个 stack |
| `HasItemAmount()` | 判断是否拥有某物品若干数量 |
| `RemoveItemAmount()` | 按数量扣除，用于交付任务和锻造 |
| `TryUseItem()` | 执行消耗品效果并扣数量 |

### 5.3 AddItem 的核心：先堆叠，后占格

```csharp
Inventory_Item itemInventory = FindStackable(itemToAdd);
if (itemInventory != null)
{
    itemInventory.AddStack();
}
else
{
    itemList.Add(itemToAdd);
}

OnInventoryChange?.Invoke();
```

代码位置：`Assets/Scripts/InventorySystem/Inventory_Base.cs:53`

这段看起来简单，但它支撑了整个背包 UI 的格子表现：`itemList` 的每一个元素就是 UI 上一个格子；`stackSize` 是格子右下角数字。

注意这里不是把 `Inventory_Item` 当作“每一件单品”，而是当作“一个物品堆叠格”。例如 5 瓶药可能是一个 `Inventory_Item`，`stackSize = 5`。

### 5.4 OnInventoryChange 是 UI 刷新的核心事件

几乎所有背包变化后都会调用：

```csharp
OnInventoryChange?.Invoke();
```

比如：

- 添加物品后：`Assets/Scripts/InventorySystem/Inventory_Base.cs:67`
- 使用消耗品后：`Assets/Scripts/InventorySystem/Inventory_Base.cs:37`
- 移除物品后：`Assets/Scripts/InventorySystem/Inventory_Base.cs:99`
- 快捷栏变化后：`Assets/Scripts/InventorySystem/Inventory_Player.cs:27`
- 仓库材料变化后：`Assets/Scripts/InventorySystem/Inventory_Storage.cs:118`

- 背包 UI 订阅玩家背包：`Assets/Scripts/UI/ChracaterUI/UI_Inventory.cs:17`
- 游戏内快捷栏订阅玩家背包：`Assets/Scripts/UI/InGameUI/UI_InGame.cs:31`
- 仓库 UI 订阅仓库：`Assets/Scripts/UI/StorageUI/UI_Storage.cs:18`
- 商店 UI 订阅玩家和商人背包：`Assets/Scripts/UI/MerchantUI/UI_Merchant.cs:20`

这就是典型的“数据驱动 UI 刷新”。UI 不需要每帧查背包，只在数据变了时刷新。

### 6.2 装备流程

玩家点击背包里的装备时，`UI_ItemSlot.OnPointerDown()` 会调用：

```csharp
inventory.TryEquipItem(itemInSlot);
```

代码位置：`Assets/Scripts/UI/ChracaterUI/UI_ItemSlot.cs:41`

`TryEquipItem()` 的流程：

```text
TryEquipItem(item)
  -> 从 itemList 找到同一个 Inventory_Item
  -> 找所有 slotType == item.itemData.itemType 的装备槽
  -> 如果有空槽，直接 EquipItem
  -> 如果没有空槽，替换第一个 matchingSlot

      -> EquipItem(新装备)
```

代码位置：`Assets/Scripts/InventorySystem/Inventory_Player.cs:51`

为什么 `slotType == item.itemData.itemType` 就能匹配？

因为装备槽也用 `ItemType` 表示类型。Player prefab 里装备槽配置为：

- `slotType: 1`，Weapon
- `slotType: 2`，Armor
- `slotType: 3`，Trink
- `slotType: 3`，第二个 Trink

代码证据：`Assets/Prefab/Player.prefab:266`

这说明项目支持 1 把武器、1 件护甲、2 个饰品。

### 6.3 EquipItem 为什么要保存血量百分比？

装备时：

```csharp
float savedHealthPercent = player.health.GetHealthPercent();

slot.equipedItem = itemToEquip;
slot.equipedItem.AddModifiers(player.stats);
slot.equipedItem.AddItemEffect(player);
player.health.SetHealthToPercent(savedHealthPercent);

RemoveOneItem(itemToEquip);
```

代码位置：`Assets/Scripts/InventorySystem/Inventory_Player.cs:72`

这个 `savedHealthPercent` 很细。

如果一件装备增加 `MaxHealth`，玩家最大生命会变化。假设你 50/100 血，装备 +100 最大生命后，如果不处理，可能变成 50/200，看起来像突然少了一半状态。项目选择保持百分比：50% 血会变成 100/200。

卸下装备也做同样处理：`Assets/Scripts/InventorySystem/Inventory_Player.cs:92`

这就是一个非常实用的主程细节：**任何会改变最大生命的装备操作，都应该决定“保留当前数值”还是“保留当前百分比”。项目选的是保留百分比。**

## 12. 存档：为什么保存 saveId 而不是保存 SO 引用？

### 12.1 GameData 保存什么

物品相关字段在 `GameData`：`Assets/Scripts/SaveSystem/GameData.cs:8`

```csharp
public int gold;
public SerializableDictionary<string, int> inventory;
public SerializableDictionary<string, int> storageItems;
public SerializableDictionary<string, int> storageMaterials;
public SerializableDictionary<string, ItemType> equipedItems;
```

这些字典的 key 是 `ItemDataSO.saveId`。

为什么不直接保存 `ItemDataSO`？

因为存档需要写成 JSON，不能可靠保存 Unity 对象引用。所以项目用 `saveId`，加载时通过 `ItemListDataSO.GetItemData(saveId)` 找回 SO。

### 12.2 saveId 来自 Asset GUID

`ItemDataSO.OnValidate()`：

```csharp
string path = AssetDatabase.GetAssetPath(this);
saveId = AssetDatabase.AssetPathToGUID(path);
```

代码位置：`Assets/Scripts/Data/ItemData/ItemDataSO.cs:36`

这意味着只要资产不被删掉重建，它的 GUID 稳定，存档就能找到它。

### 12.3 玩家背包存档

保存背包：

```csharp

{
    string saveId = item.itemData.saveId;
    if (data.inventory.ContainsKey(saveId) == false)
        data.inventory[saveId] = 0;
    data.inventory[saveId] += item.stackSize;
}
```

代码位置：`Assets/Scripts/InventorySystem/Inventory_Player.cs:105`

保存装备：

```csharp

```

代码位置：`Assets/Scripts/InventorySystem/Inventory_Player.cs:124`

这里有个重要取舍：装备只按 `saveId -> slotType` 保存，没有保存 `itemId`、随机词条、耐久、强化等级。因为当前装备数据都是静态 SO，所以够用；如果以后有随机属性，就必须扩展存档结构。

## 14. 这个系统的设计模式

| 设计模式 / 思路 | 项目实现 | 好处 |
| --- | --- | --- |
| Data-Driven | `ItemDataSO` 配物品，`ItemListDataSO` 配货池/数据库/锻造列表 | 改物品不用改代码 |
| Runtime Wrapper | `Inventory_Item` 包 `ItemDataSO` | 支持堆叠、唯一 ID、价格、运行时效果 |
| Inheritance | `Inventory_Player / Storage / Merchant` 继承 `Inventory_Base` | 复用增删查和事件刷新 |
| Observer | `OnInventoryChange` | 数据变化后 UI 自动刷新 |
| Strategy | `ItemEffect_DataSO` 子类 | 不同物品效果独立扩展 |
| Interface | `IInteractable`, `IDamagable`, `ISaveable` | 玩家交互、宝箱受击、存档都解耦 |
| Source-based Modifier | `Stat.AddModifier(value, itemId)` | 装备卸下时精准移除属性 |

最值得学习的是 `Inventory_Item.itemId` + `StatModifier.source` 这套来源追踪。它比“装备时加 10，卸下时减 10”靠谱很多。

## 15. 优点

### 15.1 UI 和数据分离

UI slot 不保存真实物品所有权。真实物品在 `Inventory_Base.itemList`，UI 每次刷新只是引用对应 `Inventory_Item`。这样不会出现 UI 关掉后物品丢失的问题。

### 15.2 背包、仓库、商店共享一套容器基类

`Inventory_Base` 抽出了 `AddItem`、`RemoveOneItem`、`FindStackable`、`CanAddItem`，避免三个系统各写一份堆叠逻辑。

### 15.3 材料自动进材料仓库

这对玩家很舒服，材料不占背包格，也方便锻造从多个容器统计材料。

### 15.4 装备效果通过事件挂接

吸血、受伤冰爆这类效果没有侵入战斗主逻辑，而是订阅 `OnDoingPhysicalDamage` / `OnTakingDamage`。后面新增“暴击回蓝”“受击召唤护盾”也可以继续做成 ItemEffect。

### 15.5 存档使用 saveId，不保存 Unity 引用

这符合 Unity 存档常规做法。JSON 里保存字符串 ID，加载时通过数据库找回 SO。

## 16. 真实风险和优化建议

### 16.1 UI 事件订阅没有取消，反复打开可能重复订阅

例如商店 UI 每次 `SetupMerchantUI()` 都会：

```csharp
this.inventory.OnInventoryChange += UpdateSlotUI;
this.merchant.OnInventoryChange += UpdateSlotUI;
```

代码位置：`Assets/Scripts/UI/MerchantUI/UI_Merchant.cs:15`

仓库 UI 和锻造 UI 也有类似订阅：`Assets/Scripts/UI/StorageUI/UI_Storage.cs:14`，`Assets/Scripts/UI/CraftUI/UI_Craft.cs:12`

如果玩家多次和商人/铁匠交互，这些订阅可能重复，导致一次背包变化触发多次 UI 刷新。表现上可能只是多刷几次，严重时会造成性能和调试困扰。

建议：

- 在 `OnDisable()` 里取消订阅。
- 或在 Setup 前先 `-=` 再 `+=`，保证只订阅一次。

### 16.2 Inventory_Storage.ConsumedMaterialsAmount 在 foreach 中 Remove

代码：

```csharp
foreach (var item in itemList)
{
    ...
    if (item.stackSize <= 0)
        itemList.Remove(item);
}
```

代码位置：`Assets/Scripts/InventorySystem/Inventory_Storage.cs:37`

C# 中在 `foreach` 遍历 List 时修改 List，通常会抛 `InvalidOperationException: Collection was modified`。即使因为 break 或当前测试没触发，也是不稳的。

建议改成倒序 for 循环，或者先记录要删除的 item，循环结束后再删除。

### 16.3 ItemEffect_DataSO 保存运行时 player，有 SO 污染风险

`ItemEffect_DataSO` 里有：

```csharp
protected Player player;
```

代码位置：`Assets/Scripts/Data/ItemData/ItemEffects/ItemEffect_DataSO.cs:7`

被动装备效果还会把 `lastTimeUsed` 这类运行时状态放在 SO asset 上，例如冰爆效果：`Assets/Scripts/Data/ItemData/ItemEffects/ItemEffect_IceBlastOnTakingDamage.cs:12`

ScriptableObject 是资产，不是普通运行时实例。在编辑器 Play Mode 中修改 SO 字段，有可能污染资产状态；多个同类装备共用同一个 effect asset 时，也会共享内部状态。

当前项目只有一个玩家，且同类唯一效果不多，所以能跑。但更稳的做法是：

- 装备时 `Instantiate(itemEffect)` 克隆一份运行时 effect。
- 或把运行时状态存到 `Inventory_Item` / 专门的 runtime effect 对象里。

### 16.4 ItemDataSO 使用 UnityEditor 命名空间

`ItemDataSO.cs` 顶部直接 `using UnityEditor;`：`Assets/Scripts/Data/ItemData/ItemDataSO.cs:1`

虽然实际调用 `AssetDatabase` 包在 `#if UNITY_EDITOR` 里，但更规范的写法是：

```csharp
#if UNITY_EDITOR
using UnityEditor;
#endif
```

否则打包时可能遇到 UnityEditor 命名空间不可用的问题。

`ItemListDataSO.cs` 也有同类问题：`Assets/Scripts/Data/ItemData/ItemListDataSO.cs:2`

### 16.5 RemoveOneItem 缺少 null 防御

`RemoveOneItem()`：

```csharp
Inventory_Item itemInInventory = itemList.Find(item => item == itemToRemove);
if (itemInInventory.stackSize > 1)
...
```

代码位置：`Assets/Scripts/InventorySystem/Inventory_Base.cs:85`

如果传进来的 item 不在当前 `itemList`，`itemInInventory` 会是 null，下一行就空引用。当前调用大多来自 UI slot，通常安全；但商店/任务/死亡掉落等路径一多，最好加保护。

建议：

```csharp
if (itemInInventory == null)
    return;
```

### 16.6 存档不保存快捷栏

`GameData` 保存了背包、装备、仓库、材料和金币，但没看到保存 `quickItems`。所以读档后快捷栏可能不会恢复。

如果要优化，可以保存：

```text
quickSlots: slotIndex -> itemSaveId
```

加载后用 `FindSameItem` 或从背包中找对应物品填回。

### 16.7 装备存档不能区分同类型同 slot 的多个饰品

当前保存装备：

```csharp
data.equipedItems[slot.equipedItem.itemData.saveId] = slot.slotType;
```

代码位置：`Assets/Scripts/InventorySystem/Inventory_Player.cs:124`

如果两个装备拥有同一个 `saveId`，字典 key 会冲突。比如未来允许装备两枚相同戒指，这个结构无法保存两个相同戒指。当前项目装备少，可能没暴露。

更稳的结构应该是：

```text
equipedSlots: slotIndex -> itemSaveId
```

而不是 `itemSaveId -> slotType`。

### 16.8 商店购买非材料时，背包满了仍可能扣钱

`TryBuyItem()` 中非材料分支：

```csharp

{
    var itemToAdd = new Inventory_Item(itemToBuy.itemData);
    inventory.AddItem(itemToAdd);
```

代码位置：`Assets/Scripts/InventorySystem/Inventory_Merchant.cs:41`

如果不是材料，且背包满、也不能堆叠，`CanAddItem()` 为 false，但后面仍然会扣金币并从商人移除物品。这是一个真实 bug。

建议：非材料且不能加入时直接 `return`，不要扣钱。

### 16.9 ItemEffect_PortalScroll 在城镇中只打印，不 return

代码：

## 17. 正面例子 vs 反面例子

### 17.1 反面：UI 里直接存物品并改属性

新手常见写法：

```csharp
public class ItemSlot : MonoBehaviour
{
    public ItemDataSO item;

    public void OnClick()
    {
        if (item.type == Weapon)
        {
            player.damage += item.damage;
            icon.enabled = false;
        }
    }
}
```

问题：

- UI 关掉或重建，物品状态容易丢。
- 装备加属性没有来源追踪，卸下困难。
- 背包、商店、仓库会各写一套逻辑。
- 存档不知道物品到底在哪。

### 17.2 正面：项目的写法

```text
ItemDataSO 只定义物品
Inventory_Item 表示运行时格子/实例
Inventory_Base 管增删堆叠
Inventory_Player 管装备/快捷栏/金币
UI_ItemSlot 只负责点击并调用 Inventory
OnInventoryChange 统一通知 UI 刷新
StatModifier.source 用 itemId 精准移除装备属性
```

这个结构的学习价值很高，因为它不是“UI 背包”，而是“数据背包 + UI 视图”。

## 18. FAQ：最容易卡住的问题

### Q1：`ItemDataSO` 和 `Inventory_Item` 到底有什么区别？

`ItemDataSO` 是物品种类，比如“Small Health potion 这种药”。  
`Inventory_Item` 是背包里的一个运行时格子，比如“我背包里这一格有 3 瓶 Small Health potion”。

一句话：SO 是图纸，Inventory_Item 是实例。

### Q2：为什么材料不进玩家背包？

因为 `Object_ItemPickup.OnTriggerEnter2D()` 对材料做了特殊处理：`ItemType.Material` 会直接进 `storage.materialStash`。这样材料不占背包格，并且锻造时自动统计。

### Q3：为什么装备时要 `RemoveOneItem()`？

因为装备栏和背包是两个位置。装备后这件物品从随身背包移到装备栏。卸下时再 `AddItem()` 回背包。

### Q4：为什么装备属性能准确卸下？

因为装备生成 `Inventory_Item` 时有唯一 `itemId`，加属性时把 `itemId` 写进 `StatModifier.source`，卸下时按这个 source 删除。

### Q5：为什么商店/仓库 UI 都用 `UI_ItemSlotParent`？

因为它们本质都是把一个 `List<Inventory_Item>` 显示成一组格子。差异不在显示，而在点击行为。所以项目让 `UI_StorageSlot`、`UI_MerchantSlot` 继承 `UI_ItemSlot` 并覆盖点击。

### Q6：为什么有些装备效果是 ExecuteEffect，有些是 Subscribe？

消耗品是一次性使用，所以走 `ExecuteEffect()`。  
装备被动效果需要持续监听玩家事件，所以装备时 `Subscribe()`，卸下时 `Unsubscribe()`。

### Q7：为什么存档保存 saveId，而不是保存 itemName？

itemName 可能改名，也可能重复。`saveId` 来自 Unity asset GUID，更稳定。加载时通过 `ITEM DATA BASE` 找回对应 SO。

### Q8：为什么锻造能用仓库里的材料？

`Inventory_Storage.GetAvailableAmountOf()` 会同时统计玩家背包、仓库普通物品、材料仓库三处。锻造消耗也按这三处依次扣。

### Q9：为什么打开商店要先走对话？

`Object_Merchant.Interact()` 先打开对话，真正打开商店由 `UI_Dialogue` 在 `DialogueActionType.OpenShop` 时调用 `OpenMerchantUI(true)`。这是对话系统和商店系统的组合。

### Q10：这个系统最该先理解哪条线？

先理解这条：

```text
ItemDataSO -> new Inventory_Item -> Inventory_Base.itemList -> OnInventoryChange -> UI_ItemSlot.UpdateSlot
```

这条线懂了，装备、仓库、商店、锻造都是在它上面加分支。

## 19. 如何迁移到自己的项目

如果你要自己做一套类似系统，建议按这个顺序：

1. 先做 `ItemDataSO`，只放静态配置。
2. 做 `Inventory_Item`，保存 `itemData`、`stackSize`、唯一 ID。
3. 做 `Inventory_Base`，实现堆叠、增删、容量、事件。
4. 做玩家背包，添加装备栏、金币、快捷栏。
5. 做 UI slot，只显示 `Inventory_Item`，点击时调用背包。
6. 做 `OnInventoryChange`，让 UI 刷新不要写在每个业务里。
7. 做场景掉落物，让它拾取时 new `Inventory_Item`。
8. 做 `ItemEffect` 策略，把消耗品和装备被动效果从背包逻辑里拆出去。
9. 最后做商店、仓库、锻造、存档。

不要一开始就从 UI 拖拽做起。背包系统的地基不是格子 UI，而是数据所有权：物品到底在哪个 List 里。

## 20. 总结

这个项目的背包与物品系统，真正的核心不是 UI，而是这三句话：

1. **`ItemDataSO` 定义物品，`Inventory_Item` 表示运行时物品格。**
2. **所有容器都围绕 `List<Inventory_Item>` 运转，变化后用 `OnInventoryChange` 通知 UI。**
3. **场景物体、商店、仓库、锻造、快捷栏都只是不同入口，最终都在操作这些 Inventory 容器。**

你如果觉得它难，可以把它想成一个物流系统：

```text
ItemDataSO = 商品 SKU
Inventory_Item = 某个货架上的一摞商品
Inventory_Base = 仓库管理规则
Inventory_Player = 玩家随身包 + 装备架 + 钱包
Inventory_Storage = 大仓库 + 材料库
Inventory_Merchant = 商人的货架
UI_ItemSlot = 货架标签
Object_ItemPickup = 地上的包裹
ItemEffect_DataSO = 商品的使用说明和特殊能力
```

把这个模型立住后，再看代码就不会被 UI、NPC、掉落、存档绕晕了。

# 属性系统深度分析

## 1. 系统定位：解决什么问题？

属性系统负责管理游戏角色所有的"数值"——包括生命值、伤害、暴击率、护甲、元素抗性等等。它的核心职责是：

1. **数值定义**：角色有哪些属性、每个属性的默认值是多少
2. **数值修改**：装备、Buff、技能如何影响属性（临时或永久）
3. **数值查询**：提供计算好的最终值给其他系统（攻击系统算伤害时问"我的伤害是多少？"）
4. **数值变化通知**：属性变了怎么通知 UI 和其他系统

**如果没有这个系统会怎样？**

你会在每个地方看到浮动的魔法数字：

```csharp
// 没有属性系统
void Attack() {
    float damage = 10f;  // 基础伤害写死
    if (hasSword) damage += 5f;  // 装备加成写死
    if (hasBuff) damage *= 1.2f;  // Buff 加成写死
}
```

装备换了要改代码、加一种新Buff要改代码、想看角色总属性无从下手。

**初学者通常会怎么实现？**

```csharp
public class Player : MonoBehaviour {
    public float damage = 10;
    public float maxHealth = 100;
    public float armor = 5;
    public float critChance = 0.1f;

    void Update() {
        if (hasSwordEquipped) damage = 15;     // 装备直接硬编码改字段
        else damage = 10;                       // 卸下又要改回来

        if (hasBuffActive) damage = damage * 1.2f;  // Buff 覆盖了装备的修改
        // 多个 Buff 叠加怎么办？卸装顺序错了数值乱掉？
    }
}
```

根本问题是：**没有区分"基础值"和"加成来源"**。改基础值会覆盖加成、多个加成来源冲突、无法精确移除某一个装备的贡献。

## 2. 设计思路：为什么这样设计？

这个项目的属性系统用了四个核心设计思路嵌套在一起：

### 2.1 核心设计：基础值 + 修饰器模式（Modifier Pattern）

**思路：** 每个属性 = 一个基础值 + 一堆修饰器（modifier）的叠加。

```
最终值 = baseValue + modifier1.value + modifier2.value + modifier3.value ...
```

每个修饰器都带一个 `source`（来源标识）。装备用 `itemId` 做来源、Buff 用 `source` 字符串做来源。这样**加来源精确，删来源也精确**：

```csharp
// 穿上一把剑：它的 itemId = "IronSword - xyz-123"
damageStat.AddModifier(5, "IronSword - xyz-123");   // damage 变成 baseValue + 5

// 脱下这把剑：用同一个 source 移除
damageStat.RemoveModifier("IronSword - xyz-123");     // 恢复成 baseValue
```

**为什么不用简单的 += 和 -= ？**

```csharp
// 反面：用 += / -=
damage += 5;  // 穿上铁剑
damage += 3;  // 又穿上一个加攻击的戒指
damage -= 5;  // 脱下铁剑 —— 结果是 damage 少了 5，但戒指的 3 还在吗？
```

用数字计算，你不知道当前 total 里包含了哪些来源。用 Modifier 模式，每个来源独立记录，互不影响。

### 2.2 脏标记模式（Dirty Flag）

每次查属性值时，不需要把 modifiers 全加一遍。只有 modifiers 变了才重新算：

```csharp
public float GetValue() {
    if (needToCaculate) {        // 脏标记：只有 true 才重新算
        finalValue = GetFinalValue();
        needToCaculate = false;  // 算完清零
    }
    return finalValue;           // 脏标记为 false 时，直接返回缓存值
}

public void AddModifier(...) {
    modifiers.Add(...);
    needToCaculate = true;       // 加 modifier → 标记脏
}
```

**好处：** 战斗中频繁读攻击力（每帧检查暴击、每次攻击算伤害），但 modifiers 只在穿/脱装备时改变。脏标记避免了每帧重复计算，性能开销降到最低。

### 2.3 分组组织

4 大类 20 个属性，如果不分组：

```csharp
public float damage, critChance, critPower, armor, evasion, fireRes, iceRes, ...  // 20个字段乱放
```

项目把它们分成 4 组，每个组一个独立类：

| 组名 | 包含属性 | 设计意图 |
|------|---------|---------|
| `Stat_MajorGroup` | strength, agility, intelligence, vitality | 四大核心属性，影响其他属性的计算 |
| `Stat_OffenseGroup` | damage, critChance, critPower, attackSpeed, armorReduction, fireDamage, iceDamage, lightningDamage | 所有进攻相关 |
| `Stat_DefenseGroup` | armor, evasion, fireRes, iceRes, lightningRes | 所有防御相关 |
| `Stat_ResourcesGroup` | maxHealth, healthRegen | 资源类属性 |

分组的好处：
- 命名空间清晰（`stats.offense.damage` vs 20 个平铺字段）
- 扩展方便——加新属性只需要在对应组加一行
- 序列化友好——Inspector 里折叠显示

### 2.4 Entity_Stats 统一入口（Facade 模式）

分组后，Entity_Stats 作为**统一入口**，封装了所有属性和计算方法：

```csharp
public class Entity_Stats : MonoBehaviour {
    // 四个组
    public Stat_ResourcesGroup resources;
    public Stat_OffenseGroup offense;
    public Stat_DefenseGroup defense;
    public Stat_MajorGroup major;

    // 提供给外部系统的计算方法
    public AttackData GetAttackData(DamageScaleData scaleData);
    public float GetPhyiscalDamage(out bool isCrit, float scaleFactor);
    public float GetElementDamage(out ElementType element, float scaleFactor);
    public float GetArmorMitigation(float armorReduction);
    public float GetEvasion();
    public float GetMaxHealth();
    public float GetElementalResistance(ElementType element);
    public Stat GetStatByType(StatType type);
}
```

其他系统（Combat、Health）只需要依赖 `Entity_Stats`，不需要关心它是内部怎么组织的。这就是**门面模式**——对外提供简单接口，对内隐藏复杂的分组逻辑。

## 4. 数据流：属性从被修改到被使用的完整路径

### 装备影响属性的流程

```
① 玩家穿上铁剑
    ↓
② Inventory_Player.EquipItem()
    ↓
③ itemToEquip.AddModifiers(player.stats)
    ↓
④ Inventory_Item.AddModifiers()
    ├─ 遍历 ironSword.modifiers[] → [{statType:Damage, value:5}]
    ├─ playerStats.GetStatByType(StatType.Damage) → 找到 offense.damage
    └─ offense.damage.AddModifier(5, "IronSword - xyz-123")
        ├─ modifiers.Add( new StatModifier(5, "IronSword - xyz-123") )
        └─ needToCaculate = true     ← 标记脏
    ↓
⑤ 玩家攻击，Entity_Combat.PerformAttack() 调用
    ↓
⑥ stats.GetPhyiscalDamage(...)      → 调用 offense.damage.GetValue()
    ↓
⑦ Stat.GetValue()
    ├─ needToCaculate == true? → 是！重新计算
    ├─ finalValue = baseValue + 5 (铁剑的 modifier)
    ├─ needToCaculate = false
    └─ 返回 finalValue
```

### Buff 影响属性的流程

```
① 玩家使用 Buff 道具
    ↓
② ItemEffect_Buff.ExecuteEffect()
    ↓
③ player.stats.ApplyBuff(buffs, duration, source)
    ↓
④ Player_Stats.BuffCo()
    ├─ activeBuff.Add(source)              ← 防止同源重复叠加
    ├─ foreach buff → GetStatByType().AddModifier(value, source)
    │   └─ 和装备走一样的 Stat.AddModifier 方法！
    ├─ yield return new WaitForSeconds(duration)  ← 等待 Buff 到期
    └─ foreach buff → GetStatByType().RemoveModifier(source)
        └─ 和卸装走一样的 Stat.RemoveModifier 方法！
```

### 属性值被消费的完整链路（以攻击为例）

```
Entity_Combat.PerformAttack()
  │
  ├─ stats.GetAttackData(basicAttackScale)    ← 问 Entity_Stats 要数据
  │   └─ new AttackData(entityStats, scaleData)
  │       ├─ GetPhyiscalDamage(out isCrit, scaleFactor)
  │       │   ├─ offense.damage.GetValue()         ← 读 Stat（含装备/Buff加成）
  │       │   ├─ major.strength.GetValue()         ← 读主属性
  │       │   ├─ GetCritChance()
  │       │   │   ├─ offense.critChance.GetValue() ← 读暴击率
  │       │   │   └─ major.agility.GetValue()*0.3  ← 敏捷加成暴击
  │       │   ├─ isCrit = Random(0,100) < critChance
  │       │   └─ return finalDamage * scaleFactor
  │       │
  │       └─ GetElementDamage(out element, scaleFactor)
  │           ├─ offense.fireDamage.GetValue()      ← 读元素伤害
  │           ├─ offense.iceDamage.GetValue()
  │           ├─ offense.lightningDamage.GetValue()
  │           ├─ major.intelligence.GetValue()       ← 智力加成元素伤害
  │           └─ 取最高 → 其他元素50% → 返回
  │
  └─ damagable.TakeDamage(physDmg, elemDmg, element, transform)
      └─ Entity_Health.TakeDamage()
          ├─ entityStats.GetEvasion()
          │   ├─ defense.evasion.GetValue()
          │   └─ major.agility.GetValue() * 0.5     ← 敏捷加成闪避
          ├─ entityStats.GetArmorMitigation(armorReduction)
          │   ├─ defense.armor.GetValue()
          │   ├─ major.vitality.GetValue()           ← 活力加成护甲
          │   └─ armor / (armor + 100)               ← 减伤公式
          ├─ entityStats.GetElementalResistance(element)
          │   ├─ defense.fireRes/iceRes/lightningRes.GetValue()
          │   └─ major.intelligence.GetValue() * 0.5  ← 智力加成抗性
          └─ finalDamage = physDmg*(1-mitigation) + elemDmg*(1-resistance)
```

关键看这里：**主属性（Strength/Agility/Intelligence/Vitality）不直接参与战斗，而是作为"系数"去加成其他属性**。

```
Strength   → + damage, + critPower
Agility    → + critChance(×0.3), + evasion(×0.5)
Intelligence → + 元素伤害, + 元素抗性(×0.5)
Vitality   → + 最大生命值(×5), + 护甲
```

这种"主属性 → 次级属性 → 最终计算"的链条，就是 RPG 游戏经典的**属性分层**设计。

## 5. 关键实现细节

### 5.1 Stat 类的脏标记实现

```csharp
// Stat.cs:6-22
[SerializeField] private float baseValue;
[SerializeField] private List<StatModifier> modifiers = new List<StatModifier>();

private bool needToCaculate = true;    // 脏标记，初始为 true
private float finalValue;              // 缓存的计算结果

public float GetValue() {
    if (needToCaculate) {              // 只有脏了才重新算
        finalValue = GetFinalValue();   // baseValue + 所有 modifier.value
        needToCaculate = false;         // 算完就干净了
    }
    return finalValue;                  // 否则直接用缓存
}
```

注意 `finalValue` 是 **private** 字段，外界无法直接修改。修改必须通过 `AddModifier` / `RemoveModifier` / `SetBaseValue`，这些方法都会自动设置 `needToCaculate = true`。这保证了缓存一致性。

### 5.2 Source 追踪

```csharp
// Stat.cs:53-63
public class StatModifier {
    public float value;
    public string source;     // 来源标识

    public StatModifier(float value, string source) {
        this.value = value;
        this.source = source;
    }
}
```

装备的 `source` 是 `"itemName - Guid"`（如 `"IronSword - xyz-123"`），Buff 的 `source` 是 `Guid.NewGuid().ToString()`。

注意装备用了 `itemName + 随机 Guid` 的组合。`itemName` 用于人类阅读，`Guid` 用于保证唯一性——如果你有两把相同的铁剑，每把生成不同的 `itemId`，脱下时只移除自己的 modifier，不会误移除另一把的。

### 5.3 属性计算公式全梳理

```csharp
// Entity_Stats.cs 中的计算方法

// 物理伤害 = 基础攻击 + 力量
GetBaseDamage() = offense.damage.GetValue() + major.strength.GetValue()

// 暴击率 = 暴击属性 + 敏捷×0.3
GetCritChance() = offense.critChance.GetValue() + major.agility.GetValue() * 0.3f

// 暴击伤害倍率 = (暴击伤害属性 + 力量×0.5) / 100
GetCritPower() = (offense.critPower.GetValue() + major.strength.GetValue() * 0.5f) / 100

// 最终伤害 = 暴击? baseDamage * critPower : baseDamage, 再×技能系数
GetPhyiscalDamage(out isCrit, scaleFactor)

// 元素伤害 = 取火/冰/雷最高 + 其他两种的50% + 智力
// 抗性 = 对应抗性属性 + 智力×0.5, 上限75%
// 护甲减伤 = 护甲/(护甲+100), 上限85%
// 闪避 = 闪避属性 + 敏捷×0.5, 上限70%
// 最大生命值 = 生命属性 + 活力×5
```

**特别注意护甲公式 `armor/(armor+100)`，这是 LOL 等游戏的标准公式：**
- armor=0 → 减伤 0%
- armor=50 → 减伤 33%
- armor=100 → 减伤 50%
- armor=200 → 减伤 66%

每一点护甲的收益是递减的（线性增加但百分比收益递减）。

### 5.4 装备/卸装的生命值百分比保持

```csharp
// Inventory_Player.cs:72-81
private void EquipItem(Inventory_Item itemToEquip, Inventory_EquipmentSlot slot) {
    float savedHealthPercent = player.health.GetHealthPercent();   // 记住当前血量百分比
    slot.equipedItem = itemToEquip;
    slot.equipedItem.AddModifiers(player.stats);                   // +装备属性（可能加最大生命值）
    slot.equipedItem.AddItemEffect(player);
    player.health.SetHealthToPercent(savedHealthPercent);          // 恢复血量百分比
}
```

为什么先记百分比、再恢复百分比？假设你先有 100/100 HP，穿上加 50 maxHP 的装备后变成 100/150。如果不处理，就等于"白嫖"了 50 血量。所以流程是：**装备前记百分比（100%）→ 装备 → 恢复成 100/150（还是 100%）**。但实际血量从 100 变成了 150，玩家感觉"穿上装备血变多了，脱下来血变少了"。

反过来，卸装备时如果先扣 maxHP 再恢复百分比，原本 150/150（100%）变成 150/100 → 100/100，血量下降但不致死。如果不恢复百分比，直接变成 150/100 就会出现当前血量超过上限的 bug。

## 6. 设计模式总结

| 模式 | 在哪体现 | 解决了什么问题 |
|------|---------|-------------|
| **Modifier 模式**（装饰器变体） | `Stat.baseValue + Stat.modifiers[]` | 多个装备/Buff 同时影响同一属性，且可精确增删 |
| **Dirty Flag 模式** | `Stat.needToCaculate` | 避免每帧重复遍历 modifiers 列表 |
| **Facade 模式** | `Entity_Stats` 统一接口 | 对外隐藏四个 StatGroup 的内部结构，简化其他系统的调用 |
| **Strategy 模式** | `GetPhyiscalDamage()` vs `GetElementDamage()` | 不同类型的伤害计算策略互相独立 |
| **Source Tracking** | `StatModifier.source` | 按来源精确移除 modifier，防止卸 A 装影响 B 装 |
| **Template Method** | `Entity_Stats` → `Player_Stats` | 基类提供通用属性计算方法，子类添加 Buff 系统扩展 |

## 7. 正面例子 vs 反面例子

### 反面：新手用 Dictionary 做属性

```csharp
public class Stats : MonoBehaviour {
    public Dictionary<string, float> stats = new();
    public Dictionary<string, List<float>> modifiers = new();

    void Start() {
        stats["damage"] = 10;
    }

    public void AddModifier(string statName, float value, string source) {
        // 新手很容易写成：
        stats[statName] += value;  // 直接改基础值！
        // 然后想移除时发现不知道减多少
    }

    public void RemoveModifier(string source) {
        // 没记录每个 source 贡献了多少，无法移除
    }
}
```

问题：用 string 做 key 拼写错误编译器不报错、直接改 baseValue 覆盖了其他来源、无法精确移除。

### 正面：项目的做法

```csharp
// 类型安全：StatType 枚举，编译器检查
public enum StatType { Damage, CritChance, ... }

// 基础值 + 记录所有来源
public void AddModifier(float value, string source) {
    modifiers.Add(new StatModifier(value, source));
    needToCaculate = true;
}

// 按来源精确移除
public void RemoveModifier(string source) {
    modifiers.RemoveAll(m => m.source == source);
    needToCaculate = true;
}

// 脏标记缓存，不重复计算
public float GetValue() {
    if (needToCaculate) {
        finalValue = baseValue + modifiers.Sum(m => m.value);
        needToCaculate = false;
    }
    return finalValue;
}
```

## 8. 易混淆点 FAQ

**Q1: `Stat.baseValue` 和 `modifiers` 有什么区别？**

`baseValue` 是角色的基础属性，由 `Stat_SetupSO` 初始化，一般在角色创建时设定，之后不变（除非升级/天赋改变）。`modifiers` 是装备、Buff、技能等外部来源的动态加成，频繁增删。最终值 = baseValue + 所有 modifier.value 之和。

**Q2: 修改 baseValue 会影响修饰器吗？**

不会。baseValue 和 modifiers 是独立存储的。`GetFinalValue()` 里是 `finalValue = baseValue` 然后遍历 modifiers 累加。所以 baseValue 变了，所有 modifier 仍然生效。这对于升级系统很重要——升级加基础属性，装备加成仍然保留。

**Q3: 为什么暴击率是 `critChance + agility*0.3` 而不是直接读一个值？**

这就是**主属性影响次级属性**的设计。敏捷不仅自己是一个独立数值，还会按比例贡献到暴击率和闪避率。这样加点时需要权衡——加敏捷既加暴击又加闪避，但不如加力量直接加伤害来得高。这是 RPG 属性平衡的经典设计。

**Q4: 元素伤害取最高而不是全部加起来，为什么？**

鼓励玩家专注培养一种元素流派。如果全部相加，玩家堆三种元素的总收益是三倍，平衡性难控制。当前设计：火 30、冰 20、雷 10 → 选择火为主元素（30）+ 冰的 50%（10）+ 雷的 50%（5）+ 智力加成 = 最终元素伤害约 45 而不是 60。

**Q5: `RemoveModifier` 的 source 匹配是精确匹配还是包含匹配？**

```csharp
modifiers.RemoveAll(modifier => modifier.source == source);
```

精确匹配。只有 source 完全相同的 modifier 被移除。这意味着装备的 `itemId`（含 Guid）必须完全一致才能移除——恰好保证了"脱下这把剑不会影响另一把剑的加成"。

**Q6: 为什么 Buff 的 source 用 `Guid.NewGuid()` 而装备用 `itemName + Guid`？**

Buff 的 source 在 `ItemEffect_Buff` 的 `[SerializeField]` 中生成，序列化到预制体上。同一个 Buff 道具的每个实例共享同一个 source。所以用 `CanApplyBuffOf(source)` 检查 `activeBuff` 列表，防止同一个 Buff 重复叠加。装备的 `itemId` 在 `Inventory_Item` 构造函数中生成，每个实例不同，所以即使两把相同的剑也可以同时装备。

**Q7: `SetBaseValue` 什么时候用？**

主要在两个场景：
1. `ApplyDefaultStatSetup()` 初始化/重置属性时
2. `AdjustStatSetup()` 动态调整敌人难度时（按 `increase`/`penalty` 系数）

普通游戏过程中不会调用 `SetBaseValue`，属性变化全部通过 Modifier 系统。

**Q8: `needToCaculate` 初始值为什么是 true？**

因为构造函数中不执行计算逻辑。Stat 类通过 `[SerializeField]` 序列化 baseValue，反序列化后 `finalValue` 的初始值是 0。第一次调用 `GetValue()` 时 `needToCaculate = true` 触发全量计算，得到正确的 finalValue。

**Q9: 为什么装备生命值装备时要保持百分比，而不是直接加 maxHP？**

```csharp
float savedHealthPercent = player.health.GetHealthPercent();
slot.equipedItem.AddModifiers(player.stats);     // 可能改变了 maxHealth
player.health.SetHealthToPercent(savedHealthPercent);
```

假设当前 100/100 HP，穿上 +50 maxHP 的装备。如果不保持百分比，变成 100/150，相当于额外给了 50 免费血量。保持百分比后变成 150/150，看起来血量没变但实际数值提升了。反过来卸装时，如果直接扣 maxHP 不恢复，可能出现 150/100 的超出上限 bug。

## 9. 总结

**属性系统的本质：** 一套带来源追踪的"基础值 + 修饰器"数值管理方案 + 脏标记缓存优化。

**最重要的类：** `Stat`（修饰器+脏标记）+ `Entity_Stats`（统一入口+计算公式）。

**核心流程一句话：** 装备/Buff 修改 Stat 的 modifiers → 标记脏 → 其他系统调 GetValue() 时自动重新计算 → 计算结果用于伤害/防御/UI 展示。

**最该学到的东西：**

1. **基础值 + 修饰器模式**是 RPG 属性系统的标准答案，它解决了"多个来源同时影响同一数值"的精确增删问题
2. **脏标记**是一种通用的缓存策略——不重复计算直到数据真正改变，适用于所有"读多写少"的场景
3. **主属性 → 次级属性**的分层设计让属性系统有深度——一个加点选择同时影响多个战斗属性，创造有意义的决策
4. **Source 追踪**是修饰器模式能工作的前提——没有它，你就无法精确移除某一个来源的贡献

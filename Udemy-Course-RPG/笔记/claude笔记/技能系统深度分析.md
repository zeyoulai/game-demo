# 技能系统深度分析

## 1. 系统定位：解决什么问题？

**系统职责**：管理玩家的 5 种主动技能——从输入触发、冷却判定、升级变体、到在场景中生成技能物体并造成伤害的**全生命周期**。

**在项目中的位置**：技能系统是连接"输入系统"和"战斗系统"的中间层——输入来了交给技能系统判断"能不能放"，能放就生成 SkillObject 进场景，SkillObject 调用战斗系统底层的 `IDamagable.TakeDamage()` 完成伤害结算。

**如果没有这个系统会怎样？**

```csharp
// 反面：在 Update 里堆 if-else
void Update() {
    if (Input.GetKeyDown(KeyCode.Q) && dashCooldown <= 0) {
        dashCooldown = 2f;
        rb.velocity = new Vector2(facingDir * 20, 0);
        Invoke(nameof(EndDash), 0.25f);
    }
    if (Input.GetKeyDown(KeyCode.E) && swordCooldown <= 0) {
        GameObject sword = Instantiate(swordPrefab, transform.position, Quaternion.identity);
        sword.GetComponent<Rigidbody2D>().velocity = mouseDir * 15;
        swordCooldown = 3f;
    }
    // 每加一个新技能，Player 类就胖一圈
}
```

问题：Player 类几百行全是技能逻辑、冷却用散装 float 变量互相踩踏、技能升级变体无法管理、存档读档无从下手。

## 2. 设计思路：为什么这样设计？

### 2.1 核心架构决策：Skill（逻辑） + SkillObject（表现）双层分离

这是本系统最重要的设计决策。类比一下：

| 层 | 类 | 挂在哪里 | 职责 | 类比 |
|----|-----|---------|------|------|
| **逻辑层** | `Skill_Base` 子类 | Player 身上的 Component | 冷却、升级状态、能否使用 | **遥控器** |
| **表现层** | `SkillObject_Base` 子类 | `Instantiate` 生成的 Prefab | 物理运动、碰撞检测、伤害结算 | **飞出去的实体** |

为什么要拆成两层？因为技能的两个维度——"什么时候能放"和"放出去之后怎么表现"——变化节奏完全不同：

- 冷却/升级状态在整个游戏过程中持续存在，要存档、要联网同步、要看 UI 冷却转圈
- SkillObject 是瞬时的——生成、飞行、命中、销毁，生命周期只有几秒

如果把它们写在一个类里，销毁 SkillObject 时也销毁了冷却状态和升级信息——你还得额外想办法把这些数据"转移"到 Player 上。不如一开始就分开。

### 2.2 为什么 Skill_Base 是 MonoBehaviour 而不是 SO 或纯 C# 类？

你可能想：技能数据不是最适合做 SO 吗？

实际上项目是这样分的：
- `Skill_DataSO`（SO）— 存**静态配置**：技能名、图标、升级后的冷却和伤害系数
- `Skill_Base`（MonoBehaviour）— 存**运行时状态**：`lastTimeUsed`、当前 `upgradeType`、冷却倒计时

SO 管"这个技能是什么"，Component 管"这个技能现在冷却好了没"。泾渭分明。

MonoBehaviour 的另一个好处是 `Invoke` / `StartCoroutine` 可以直接用（虽然本项目技能没怎么用），并且能通过 `GetComponentInChildren<Skill_Dash>()` 的方式让 `Player_SkillManager` 统一管理。

### 2.3 升级系统：一个 enum，N 种行为

每个技能有多个升级变体，项目用一个 `SkillUpgradeType` 枚举表达了所有可能：

```
SkillUpgradeType:
  None → 技能未解锁
  Dash → 基础冲刺
  Dash_CloneOnStart → 冲刺开始时留下残影分身
  Dash_CloneOnStartAndArrival → 起止各留一个分身
  ...
  SwordThrow → 基础投剑
  SwordThrow_Pierce → 穿透剑
  SwordThrow_Spin → 旋转剑
  SwordThrow_Bounce → 弹射剑
  ...
```

升级节点被点击 → `UI_TreeNode.Unlock()` → `skill.SetSkillUpgrade(Skill_DataSO)` → 更新 `upgradeType`、`cooldown`、`damageScaleData`。

技能内部用 `Unlocked(SkillUpgradeType.xxx)` 判断当前版本：

```csharp
// Skill_Dash.cs:21-26
if (Unlocked(SkillUpgradeType.Dash_CloneOnStart) || Unlocked(SkillUpgradeType.Dash_CloneOnStartAndArrival))
    CreateClone();

if (Unlocked(SkillUpgradeType.Dash_ShardOnStart) || Unlocked(SkillUpgradeType.Dash_ShardOnStartAndArrival))
    CreateShard();
```

**这个设计的精妙之处**：新增一个升级变体只需：① 在 `SkillUpgradeType` 枚举加一项 ② 在 SO 资源里配置新的 `Skill_DataSO` ③ 在技能类里加一个 `if (Unlocked(...))`。改动范围完全局限在该技能类内部。

### 2.4 为什么 Dash 和 Shard/TimeEcho 的输入入口不同？

看输入绑定：

```csharp
// Player.cs:215-216 — Shard 和 TimeEcho 直接绑输入
input.Player.Spell.performed += ctx => skillManager.shard.TryUseSkill();
input.Player.Spell.performed += ctx => skillManager.timeEcho.TryUseSkill();

// PlayerState.cs:29-33 — Dash 在状态机层检测
if (input.Player.Dash.WasPressedThisFrame() && CanDash())
    stateMachine.ChangeState(player.dashState);

// PlayerState.cs:34-46 — Ultimate 也在状态机层
if (input.Player.UltimateSpell.WasPressedThisFrame() && skillManager.domainExpansion.CanUseSkill())
    stateMachine.ChangeState(player.domainExpansionState);

// Player_SwordThrowState.cs:27 — SwordThrow 在专用状态里检测
if (input.Player.Attack.WasPerformedThisFrame()) ...
```

这看起来很不一致，但背后有各自的原因：
- **Dash** 需要进专用状态（`Player_DashState`），因为要控制重力、无敌帧、Layer 切换——这些是状态机管的
- **Domain** 需要进专用状态（`Player_DomainExpansionState`），因为要升空动画+悬停
- **SwordThrow** 需要专用状态（`Player_SwordThrowState`），因为要显示瞄准轨迹
- **Shard/TimeEcho** 不需要状态切换——角色原地释放，不改变移动/物理行为，直接 `TryUseSkill()` 就够了

所以这不是混乱，而是"需不需要状态机接管角色行为"的务实分类。如果你觉得不统一，可以给所有技能都做状态，但 Shard/TimeEcho 的状态只是空转一帧就退出——那才是多余的设计。

| `UI_TreeNode` | MonoBehaviour | 单个技能节点 | `skillData`, `isUnlocked`, `isLocked`; `Unlock()`, `CanBeUnlocked()`, `Refund()` | 挂在 `UI_SkillTree` 下 |

## 5. 运行流程

### 5.1 技能完整生命周期（以投剑为例）

```
【解锁阶段 — 技能树】
玩家在技能树UI点击节点
  │
  ▼
UI_TreeNode.OnPointerDown()
  ├─ CanBeUnlocked() → 检查前置节点、冲突节点、技能点够不够
  └─ Unlock()
       ├─ skillTree.RemoveSkillPoints(cost)
       └─ skillManager.GetSkillByType(SkillType.SwordThrow)
           .SetSkillUpgrade(skillData)              ← ★ 激活技能
              ├─ this.cooldown = upgrade.cooldown    ← 冷却时间
              ├─ this.upgradeType = upgrade.upgradeType ← 变体类型
              ├─ this.damageScaleData = upgrade.damageScaleData ← 伤害系数
              ├─ ReSetCooldown()                    ← 冷却直接归零，立即可用
              └─ player.ui.inGameUI.GetSkillSlot(skillType)
                  .SetupSkillSlot(skillData)        ← UI显示图标

【使用阶段 — 运行时】
T=0ms    玩家按住 RangeAttack 键
         PlayerState.Update() 检测到
         → stateMachine.ChangeState(swordThrowState)

T=16ms   Player_SwordThrowState.Enter()
         ├─ skillManager.swordThrow.EnableDots(true)  ← 显示弹道预测点
         └─ mainCamera = Camera.main

T=16~    Player_SwordThrowState.Update() 每帧:
         ├─ Vector2 dirToMouse = DirectionToMouse()
         ├─ player.HandleFlip(dirToMouse.x)          ← 朝向鼠标
         ├─ skillManager.swordThrow.PredictTrajectory(dirToMouse)
         │    └─ 每帧更新 20 个预测点的位置（抛物线公式）
         │
         └─ if(Attack.WasPerformedThisFrame())        ← 玩家松手/确认
              ├─ anim.SetBool("swordThrowPerformed", true)
              ├─ EnableDots(false)                    ← 隐藏预测点
              └─ confirmTrajectory(dirToMouse)         ← 锁定方向

T=200ms  ★ Animation Event: "ThrowSword()"           ← Player_AnimationTriggers
         → skillManager.swordThrow.ThrowSword()

         ThrowSword() 内部:
         ├─ GetSwordPrefab() → 根据 upgradeType 选 Prefab
         │   ├─ SwordThrow → 普通剑
         │   ├─ SwordThrow_Pierce → 穿透剑
         │   └─ SwordThrow_Spin → 旋转剑
         ├─ Instantiate(swordPrefab, dots[1].position, Quaternion.identity)
         ├─ currentSword.SetupSword(this, GetThrowPower())  ← 传递参数
         │    └─ rb.linearVelocity = direction
         │    └─ playerStats = swordManager.player.stats
         │    └─ damageScaleData = swordManager.damageScaleData
         └─ SetSkillOnCooldown()
              ├─ lastTimeUsed = Time.time                    ← 开始冷却
              └─ UI 冷却转圈动画

T=300ms  剑在空中飞行
         SkillObject_Sword.Update():
         ├─ transform.right = rb.linearVelocity    ← 剑尖朝飞行方向
         └─ HandleComeback() → 超距离自动回收

T=500ms  剑碰到敌人 → OnTriggerEnter2D()
         ├─ StopSword(collider) → rb.simulated = false   ← 停止物理
         └─ DamageEnemiesInRadius(transform, 1)            ← 范围伤害
              ├─ GetEnemiesAround() → Physics2D.OverlapCircleAll
              ├─ playerStats.GetAttackData(damageScaleData) ← ★ 算伤害
              ├─ damagable.TakeDamage(...)                  ← 走战斗系统
              └─ Instantiate(onHitVfx, ...)                 ← 命中特效

T=600ms  如果剑是穿透剑(SwordPeirce): 不停，继续飞，amountToPeirce--
         如果剑是旋转剑(SwordSpin): 停住，每 1/6 秒范围攻击一次，4秒后回收
         如果剑是弹射剑(SwordBounce): 停住，选最近的活的敌人弹过去

T=1500ms 剑回到玩家身边 (<0.5f) → Destroy(gameObject)
```

### 5.2 Dash 不同入口的流程

```
Dash 有两个入口：

入口 1 — 玩家主动按 Dash 键:
  PlayerState.Update() → Dash.WasPressedThisFrame() + CanDash()
  → stateMachine.ChangeState(dashState)
  → Player_DashState.Enter()
      ├─ skillManager.dash.OnStartEffect()
      │    ├─ Unlocked(Dash_CloneOnStart) → skillManager.timeEcho.CreateTimeEcho()
      │    └─ Unlocked(Dash_ShardOnStart) → skillManager.shard.CreateRawShard()
      ├─ player.vfx.DoImageEchoEffect()              ← 残影拖尾
      ├─ rb.gravityScale = 0                          ← 零重力
      ├─ player.health.SetCanTakenDamage(false)       ← 无敌
      └─ player.gameObject.layer = "Untargetable"     ← 不可被锁定

  Player_DashState.Update():
      player.SetVelocity(dashSpeed * dashDir, 0)     ← 恒定速度冲刺
      if(stateTimer < 0) → Exit

  Player_DashState.Exit():
      ├─ skillManager.dash.OnEndEffect()
      │    ├─ Unlocked(Dash_CloneOnStartAndArrival) → CreateClone()
      │    └─ Unlocked(Dash_ShardOnStartAndArrival) → CreateShard()
      ├─ rb.gravityScale = orginalGravityScale        ← 恢复重力
```

## 6. 关键实现细节

### 6.1 冷却系统：简单的 `Time.time` 对比

```csharp
// Skill_Base.cs:73-78
protected bool OnCooldown() => Time.time < lastTimeUsed + cooldown;

public void SetSkillOnCooldown()
{
    player.ui.inGameUI.GetSkillSlot(skillType).StartCooldown(cooldown);
    lastTimeUsed = Time.time;
}
```

没有用协程、没有用定时器、没有用 `Invoke`。只有一行 `Time.time < lastTimeUsed + cooldown`。简单、无 GC、不受 `timeScale` 之外的任何因素影响。

UI 冷却转圈独立管理（`StartCooldown(cooldown)`）——UI 走自己的计时，不和技能逻辑层的 `OnCooldown()` 耦合。这样即使 UI 被禁用，冷却逻辑仍然正常工作。

### 6.2 冷却缩减的实现：不是改 `cooldown` 而是改 `lastTimeUsed`

```csharp
// Skill_Base.cs:80
public void ReduceCooldownBy(float cooldownReduction)
    => lastTimeUsed = lastTimeUsed + cooldownReduction;
```

你可能想：为什么不直接 `cooldown -= cooldownReduction`？因为 `cooldown` 是技能的基础冷却时间，不应该被修改——否则下一次冷却也会被影响。改 `lastTimeUsed`（把上次使用时间向前挪）只影响当前周期的冷却，不影响后续。**把副作用局限在当前周期，不污染配置值**——这是好的设计习惯。

### 6.3 弹道预测：物理驱动的抛物线

```csharp
// Skill_SwordThrow.cs:116-128
private Vector2 GetTrajectoryPoint(Vector2 direction, float t)
{
    float scaledThrowPower = currentThrowPower * 10;
    Vector2 initialVeclocity = direction * scaledThrowPower;
    Vector2 gravityEffect = 0.5f * Physics2D.gravity * swordGravity * (t * t);

    Vector2 predictedPoint = (initialVeclocity * t) + gravityEffect;
    Vector2 playerPosition = transform.root.position;

    return playerPosition + predictedPoint;
}
```

这不是猜测，而是**真正使用和剑的 Rigidbody2D 相同的物理参数**（`Physics2D.gravity` × `swordGravity`）来计算弹道。预测点和实际飞行轨迹完全一致。

20 个预测点（`numberOfDots = 20`），间隔 `spaceBetweenDots = 0.05s`，覆盖 1 秒的飞行时间。每个点是一个独立的 GameObject，被放在 Player 的子物体下（`Instantiate(predictionDot, ..., transform)`），开启/关闭通过 `SetActive` 切换。

### 6.4 SkillObject 的参数传递：Setup 模式

所有的 SkillObject 都遵循相同的模式——创建后不依赖 Awake/Start 中的查找，而是通过显式的 `SetupXxx()` 方法接收参数：

```csharp
// Skill_SwordThrow.cs:65-67
GameObject newSword = Instantiate(swordPrefab, dots[1].position, Quaternion.identity);
currentSword = newSword.GetComponent<SkillObject_Sword>();
currentSword.SetupSword(this, GetThrowPower());   // ← 显式传参

// SkillObject_Sword.cs:20-29
public virtual void SetupSword(Skill_SwordThrow swordManager, Vector2 direction)
{
    rb.linearVelocity = direction;
    this.swordManager = swordManager;
    playerTransform = swordManager.transform.root;
    playerStats = swordManager.player.stats;         // ← 从 Skill 传给 SkillObject
    damageScaleData = swordManager.damageScaleData;  // ← 伤害系数也传过来
}
```

为什么不用 `GetComponent` 或单例？因为 SkillObject 是 `Instantiate` 出来的独立 GameObject，它和 Player 之间没有层级关系（不在 Player 的子物体下），`GetComponentInParent` 找不到。最干净的做法就是**创建方显式传参**。

### 6.5 领域展开的缩放动画

```csharp
// SkillObject_DomainExpansion.cs:33-46
private void HandleScaling()
{
    float sizeDiffrence = Mathf.Abs(transform.localScale.x - targetScale.x);
    bool shouldChangeScale = sizeDiffrence > 0.1f;

    if (shouldChangeScale)
        transform.localScale = Vector3.Lerp(transform.localScale, targetScale, expandSpeed * Time.deltaTime);

    if (isShrinking && sizeDiffrence < 0.1f)
        TerminateDomain();                         // ← 缩到 0 时销毁
}
```

展开时 `targetScale = Vector3.one * maxDomainSize`，用 `Lerp` 平滑放大。`Invoke` 在 `duration` 秒后切 `targetScale = Vector3.zero` + `isShrinking = true`，缩到接近 0 时销毁。**没有用 Animator 做缩放**，纯代码控制——好处是展开速度 `expandSpeed` 可配置，不受动画资源限制。

### 6.6 TimeEcho 的分身攻击 + Wisp 系统

这是本项目最复杂的 SkillObject。它有一个两阶段生命周期：

```
第一阶段：分身存在
  SetupEcho() → Invoke(nameof(HandleDeath), duration) ← 定时死亡
  如果有 maxAttacks > 0:
    Animation Event: "AttackTrigger()" → PerformAttack()
      ├─ DamageEnemiesInRadius() → 造成伤害
      ├─ 有 duplicateChance 概率 → echoManager.CreateTimeEcho(新位置) ← 分裂！
      └─ Animation Event: "TryTerminate()" → 攻击次数到上限 → HandleDeath()

第二阶段：Wisp（如果升级了 HealWisp / CleanseWisp / CooldownWisp）
  HandleDeath() → TurnToWisp()
    ├─ shouldMoveToPlayer = true
    ├─ anim.gameObject.SetActive(false)           ← 隐藏动画
    ├─ wsipTrail.gameObject.SetActive(true)       ← 显示拖尾
    └─ rb.simulated = false                       ← 关闭物理

  Update() → HandleWispMovement()
    ├─ getCurveDir() → PerlinNoise 曲线飞行      ← ★随机漂移！
    ├─ 飞向玩家
    └─ 到达玩家 (距离<0.2f) → HanldePlayerTouch()
         ├─ 回血 (damagePercentHealed)
         ├─ 减所有技能冷却 (cooldownReducedInSeconds)
         └─ 清除负面效果 (CanRemoveNegativeEffects)
```

Wisp 的飞行用了 `Mathf.PerlinNoise` 做曲线抖动，不是直线飞向玩家——视觉上更像"灵魂飘回来"的感觉。注意 `noiseSeed` 是 `Start()` 中随机的，每个 Wisp 的飞行轨迹都略有不同。

### 6.7 水晶传送的交换逻辑

```csharp
// Skill_Shard.cs:106-115
private void SwapPlayerAndShard()
{
    Vector3 shardPosition = currentShard.transform.position;
    Vector3 playerPosition = player.transform.position;

    currentShard.transform.position = playerPosition;   // ← 水晶移到玩家位置
    currentShard.Explode();                              // ← 原位置爆炸

    player.TeleportPlayer(shardPosition);                // ← 玩家瞬移到水晶位置
}
```

第一次按技能键：生成水晶在原地，启动延时。第二次按：**交换**——玩家和水晶互换位置，水晶在原来玩家的位置爆炸（有伤害判定），玩家出现在水晶之前的位置。这个设计很巧妙：两次按键对应两个不同的操作阶段，用 `currentShard == null` 来判断当前处于哪个阶段。

### 6.8 多重水晶的充能系统

```csharp
// Skill_Shard.cs:118-142
private void HandleShardMulticast()
{
    if (currentCharges <= 0) return;

    CreateShard();                                    // 立即创建一个
    currentShard.MoveTowardsClosestTarget(shardSpeed); // 飞向最近的敌人
    currentCharges--;                                  // 耗一层充能

    if (isRecharging == false)
        StartCoroutine(ShardRechargeCo());             // 启动充能协程
}

private IEnumerator ShardRechargeCo()
{
    isRecharging = true;
    while (currentCharges < maxCharge)
    {
        yield return new WaitForSeconds(cooldown);     // ← 每 cooldown 秒回一层
        currentCharges++;
    }
    isRecharging = false;
}
```

`maxCharge = 3`，初始 3 层。放一个少一层，每 `cooldown` 秒回一层。这是一个类似 MOBA 游戏"充能型技能"的实现——不共享冷却，每层有自己的回复计时。

### 6.9 技能互斥节点

```csharp
// UI_TreeNode.cs:123-129
private void LockConflictNodes()
{
    foreach (var node in conflictNodes)
    {
        node.isLocked = true;
        node.LockChildrenNodes();       // ← 递归锁住冲突节点的所有子节点
    }
}
```

技能树支持互斥分支设计：同一层级的多个升级变体互为冲突节点，选了 `SwordThrow_Pierce` 就锁住 `SwordThrow_Spin` 和 `SwordThrow_Bounce`。`LockChildrenNodes()` 递归锁住冲突节点的所有后代——因为如果你不能选 Spin，那 Spin 的子升级也不能选。

## 7. 优化手段

### 7.1 GetComponentInChildren 聚合在 Awake 中一次完成

```csharp
// Player_SkillManager.cs:14-21
private void Awake()
{
    dash = GetComponentInChildren<Skill_Dash>();
    shard = GetComponentInChildren<Skill_Shard>();
    // ... 全部在 Awake 中一次性获取并缓存
    allSkills = GetComponentsInChildren<Skill_Base>();
}
```

所有技能组件的引用在 `Awake` 中缓存，运行时通过属性访问无开销。

### 7.2 预测点池化（事实上的静态池）

```csharp
// Skill_SwordThrow.cs:142-152
private Transform[] GenerateDots()
{
    Transform[] newDots = new Transform[numberOfDots];  // 20 个
    for (int i = 0; i < numberOfDots; i++)
    {
        newDots[i] = Instantiate(predictionDot, transform.position, Quaternion.identity, transform).transform;
        newDots[i].gameObject.SetActive(false);          // 预创建，关掉
    }
    return newDots;
}
```

20 个预测点只在 `Awake` 中创建一次，之后永不销毁。使用时 `SetActive(true/false)` 切换，零 GC。虽然没用 Queue/Stack，但这就是一种静态池——数量固定、预创建、循环使用。

### 7.3 技能状态在构造函数中创建（不是运行时 new）

五个技能相关的 PlayerState（`DashState`、`SwordThrowState`、`DomainExpansionState`）全部在 `Player.Awake()` 中一次 new 出来，和普通状态一样走零 GC 的状态机模式。

## 10. 易混淆点 FAQ

**Q1: 为什么 Dash 用状态机状态，而 Shard/TimeEcho 不用？**

Dash 需要改变角色的物理行为（零重力、恒定速度、无敌、Layer 切换），这些属于状态机管的"角色行为模式切换"。Shard/TimeEcho 是"角色原地释放，技能物体飞出去"，角色自己不受影响，不需要状态切换。SwordThrow 需要专用状态是因为瞄准时需要冻结移动（`SetVelocity(0, rb.linearVelocityY)`）并显示轨迹。

**Q2: 为什么 `Skill_Dash.OnStartEffect()` 里调 `skillManager.timeEcho.CreateTimeEcho()`？Dash 和 TimeEcho 不是两个独立技能吗？**

这是 Dash 升级后的效果——Dash_CloneOnStart 升级让冲刺开始时自动放一个 TimeEcho 分身。本质上是一种"升级后技能 A 触发技能 B"的跨技能组合。因为 `Skill_Dash` 持有 `skillManager` 引用，所以能访问任何其他技能。这是一种务实的做法，但如果跨技能组合太多，建议用事件系统解耦。

**Q3: `Skill_SwordThrow.Update()` 中 `UpdataThrowPower()` 会被频繁调用吗？**

`UpdataThrowPower()` 在 `CanUseSkill()` 中被调用——也就是**每次按技能键时调一次**，不是每帧。所以即使它内有一个 `switch(upgradeType)` 也不算浪费。

**Q4: 弹射剑的 `GetNextTarget()` 会弹回已经打过的敌人吗？**

`selectedBefore` 列表记录了弹过的所有敌人，`GetValidTargets()` 会过滤掉它们。如果所有存活的敌人都被弹过了，`selectedBefore.Clear()` 清空记录后重新从存活的敌人中随机选——所以弹射剑可以在多个敌人之间循环弹射直到 `bounceCount` 用完。

**Q5: 为什么 `SkillObject_Base` 中同时有 `targetCheck` 和直接用 `transform` 传参？**

`targetCheck` 是 Inspector 中配置的子物体 Transform，允许策划调整检测圆心位置（比如把检测圆放在剑尖而不是剑柄）。`DamageEnemiesInRadius(Transform t, float radius)` 接受任意 Transform 作为圆心，给了调用方灵活性——`SwordSpin` 传 `transform`（剑自身），`SwordBounce` 传 `transform`（弹射时也是剑自身），但 `SkillObject_TimeEcho.PerformAttack()` 传的是 `targetCheck`（配置在 Prefab 上的检测点）。

**Q6: 领域展开的 `Domain_ShardSpam` 和 `Domain_EchoSpam` 为什么在自己的状态里而不是领域内部处理？**

`DoSpellCasting()` 在 `Player_DomainExpansionState.Update()` 中每帧调用——这意味着法术施放逻辑虽然属于领域技能，但由状态机驱动。原因是施法需要持续访问 `Player`（创建 Shard/Echo 需要 Player 的位置），而领域展开期间 Player 处于悬停状态。如果施法逻辑放在 `SkillObject_DomainExpansion` 里，领域物体就得持有对 Player 的引用并通过 `Update` 驱动——和现在的设计只是调用方向不同，效果一样。

**Q7: `WashAllSkills()` 把所有技能设为 `None`，之后怎么恢复？**

`WashAllSkills()` 在 `UI_TreeNode.RefundAllSkills()` 流程中被调用（技能树一键重置）。重置后所有技能回到未解锁状态。加载存档时，`UI_SkillTree.LoadData()` 逐个恢复：先从 `data.skillTreeUI` 恢复节点的解锁状态，再从 `data.skillUpgrades` 恢复每个技能的升级类型。

**Q8: 冷却缩减 `ReduceCooldownBy` 传入负数会怎样？**

会让 `lastTimeUsed` 变小，冷却反而变长。没有做参数校验（`Mathf.Max(0, cooldownReduction)`），因为调用方（`TimeEcho` 的 CooldownWisp）传入的是正数。但如果将来某个效果想做"增加冷却时间"，这个函数自然地支持了——虽然这可能是无意的。

## 11. 如何迁移到自己的项目

**可直接复用的部分：**
- `Skill_Base` 的冷却管理逻辑（`OnCooldown()` / `SetSkillOnCooldown()` / `ReduceCooldownBy()`）——纯 `Time.time` 方案，零依赖
- Skill（逻辑）+ SkillObject（表现）双层分离模式——适合所有"角色释放→生成物体→物体独立运作"的技能类型
- `UpgradeType` 枚举 + `Unlocked()` 判断模式——简单有效的升级分支方案
- `Skill_SwordThrow` 的弹道预测——抛物线公式通用，改物理参数即可适配

**需要改造的部分：**
- 输入绑定方式：项目用了 Unity Input System，如果你用旧版 Input Manager 需要改
- `SkillObject_Base.DamageEnemiesInRadius()` 依赖 `Entity_Stats` 和 `IDamagable`——需要适配你自己的属性/战斗系统
- 技能树 UI 完全用 uGUI 手写——界面部分需要根据自己的 UI 框架重做

**Unity 编辑器中要重新配置：**
- 每个技能 Prefab 的 `targetCheck` 子物体和 `checkRadius`
- `whatIsEnemy` LayerMask
- 所有 Animation Event（`ThrowSword()`、`AttackTrigger()`、`TryTerminate()`）
- `Skill_DataSO` 资源（每个技能+每种升级各一个 SO）

## 12. 总结

**技能系统的本质：Skill（逻辑组件，管"能不能放"）+ SkillObject（场景物体，管"放出来怎样"）双层分离 + 枚举驱动的升级分支系统。**

**最重要的类：**
- `Skill_Base` — 所有技能的冷却和升级基类，定义了一致的行为接口
- `SkillObject_Base` — 所有技能物体的物理/伤害基类，`DamageEnemiesInRadius()` 是可复用的核心
- `Player_SkillManager` — 聚合所有技能的中控，统一管理冷却缩减
- `UI_TreeNode` — 技能树节点，通过 `conflictNodes` 数组实现互斥分支

**核心流程一句话：** 输入触发 → `CanUseSkill()` 检查（解锁+冷却）→ `TryUseSkill()` → `Instantiate(SkillObject Prefab)` → `SetupXxx()` 传参 → SkillObject 在场景中运动/碰撞 → `DamageEnemiesInRadius()` 结算伤害 → 自销毁。

**最该学到的东西：**
1. **双层分离让"可复用"和"可替换"各自独立**——换一个技能物体 Prefab 不影响冷却逻辑，改冷却方式不影响伤害结算
2. **枚举驱动的升级分支比继承树更轻量**——5 个技能 × 平均 4 种升级 = 20 种行为，如果全用继承就是 20 个类，枚举 + `Unlocked()`判断只有 5 个类
3. **显式 Setup 优于隐式查找**——SkillObject 不靠 `GetComponent`/单例找引用，所有依赖由创建方通过参数传入，契约清晰

# 输入系统深度分析

## 1. 系统定位：解决什么问题？

### 系统职责

这个项目的输入系统负责**将所有玩家输入（键盘+鼠标）转化为游戏内的行为调用**，核心任务包括：

- **按键映射**：将物理按键（WASD/空格/鼠标左右键等）映射为语义化的游戏动作（Movement/Jump/Attack/Spell 等）
- **多设备支持**：同一套逻辑能响应键盘或手柄（虽然本项目实际只绑了键盘+鼠标）
- **输入上下文隔离**：战斗时按键=攻击，UI打开时同样的按键=菜单导航，互不干扰
- **状态感知**：同一个 Attack 键，在地面=普攻，在空中=跳劈，在蓄力状态=确认释放飞剑——由状态机决定具体行为

### 如果没有这个系统会出什么问题

初学者会直接在 `Update()` 里写 `Input.GetKeyDown(KeyCode.Space)` 之类。问题很明显：

- 按键和逻辑硬耦合，想改键位只能改代码
- 每帧 `Input.GetKey` 读的是当前帧状态，多人本地合作时无法区分哪个玩家按的
- UI 打开时要写一堆 `if (uiOpen) return;` 来屏蔽输入，散落各处
- 想支持手柄？全部重写

### 初学者通常会怎么粗暴实现

```csharp
// 反面教材：每帧轮询硬编码按键
void Update()
{
    float h = Input.GetAxis("Horizontal");
    float v = Input.GetAxis("Vertical");
    
    if (Input.GetKeyDown(KeyCode.Space))
        Jump();
    if (Input.GetMouseButtonDown(0))
        Attack();
    if (Input.GetKeyDown(KeyCode.E))
        UseQuickItem();
    // ...想加手柄？再写一套 else if
}
```

## 2. 设计思路：为什么这样设计？

### 架构选型：三种使用新输入系统的方式

Unity 新输入系统提供了三种接入方式：

| 方式 | 做法 | 本项目用了没 |
|------|------|------------|
| **PlayerInput 组件** | 挂 MonoBehaviour，拖 `.inputactions` 到 Inspector，通过 UnityEvent 或 `SendMessage`/Broadcast 调用方法 | **没用** |
| **InputActionAsset 代码生成** | 在 `.inputactions` 上勾选 "Generate C# Class"，生成强类型包装类，代码里 `new` 出来用 | **用了（PlayInputSet.cs）** |
| **手动创建 InputAction** | 纯代码 `new InputAction(...)` 逐个创建，不用 `.inputactions` 文件 | 没用 |

**为什么选"代码生成"而不是 PlayerInput 组件？**

PlayerInput 组件的问题在于它通过 `SendMessage` 或 `UnityEvent` 把输入分发出去，这种字符串反射式调用在复杂项目中很难追踪。而这个项目的状态机架构要求**每个状态独立决定如何处理同一按键**——`PlayerInput.SendMessage("OnAttack")` 只会调到一个方法，没法做到"地面状态里 Attack=普攻，空中状态里 Attack=跳劈"。

代码生成方案给了你一个强类型的 `PlayerInputSet` 对象，你可以在任意代码位置通过 `input.Player.Attack.WasPressedThisFrame()` 读取。**输入和消费完全解耦**，这才是状态机友好型方案。

### 为什么采用"事件驱动 + 状态轮询"混合模式？

这个项目把输入分成了两类，用不同方式消费：

**第一类：持续型输入——用事件订阅（event-driven）**

```csharp
// Player.cs :210-213 —— 在 OnEnable 中订阅事件，持续更新字段
input.Player.Mouse.performed += ctx => mousePosition = ctx.ReadValue<Vector2>();
input.Player.Movement.performed += context => moveInput = context.ReadValue<Vector2>();
input.Player.Movement.canceled += ctx => moveInput = Vector2.zero;
```

Movement 和 Mouse 是**每帧都需要知道当前值**的输入。如果用事件，只需要在值变化时更新字段，状态机里的任何状态都能随时读 `player.moveInput`。如果用轮询，每个状态都要写 `input.Player.Movement.ReadValue<Vector2>()`，冗余且低效。

**第二类：离散型输入——用状态轮询（polling）**

```csharp
// Player_GroundedState.cs :17 —— 在状态 Update 中轮询
if (input.Player.Jump.WasPressedThisFrame())
{
    stateMachine.ChangeState(player.jumpState);
}
```

Attack、Jump、Dash、CounterAttack 这些是**一次性触发、上下文敏感**的输入。同一个按键在不同状态做不同的事——这正是状态机的优势。把这个逻辑放在每个状态的 `Update()` 里，让每个状态自己决定"这个按钮对我意味着什么"。

**关键设计决策：全局输入放 PlayerState 基类，特定输入放子类**

```csharp
// PlayerState.cs :29-33 —— 所有状态共享的全局输入
// Dash 和 UltimateSpell 在任何状态都能触发
if (input.Player.Dash.WasPressedThisFrame() && CanDash())
{
    skillManager.dash.SetSkillOnCooldown();
    stateMachine.ChangeState(player.dashState);
}
```

而 Attack 则分层处理：

- `Player_GroundedState.Update()` → 检测 Attack → 进入 `BasicAttackState`
- `Player_AirState.Update()` → 检测 Attack → 进入 `JumpAttackState`
- `Player_BasicAttackState.Update()` → 检测 Attack → 排队下一次连击

### 和 Unity 旧输入系统的对比

| | 旧 Input Manager | 新 Input System（本项目） |
|---|---|---|
| 配置方式 | `Edit > Project Settings > Input Manager` | `.inputactions` 资源文件（JSON） |
| 按键映射 | 字符串名称如 "Horizontal"、"Fire1" | 语义化 Action 如 "Attack"、"Jump" |
| 多设备 | 需要写额外代码切换 | 同一 Action 自动绑定多设备 |
| 读输入 | `Input.GetKeyDown(KeyCode.Space)` | `input.Player.Jump.WasPressedThisFrame()` |
| 本地多人 | 不支持 | 通过 `PlayerInput` 组件或设备索引原生支持 |
| 编译时检查 | 无（字符串魔法值） | 有（生成的 C# 类，属性名拼错编译报错） |

## 6. 关键实现细节

### 6.1 `.inputactions` 资源配置

项目实际使用的是 `PlayInputSet.inputactions`（`InputSystem_Actions.inputactions` 是 Unity 默认模板，虽然存在但代码中未引用）。

**Player Action Map（12 个 Action）：**

| Action | Type | 键盘绑定 | 代码中消费方式 |
|--------|------|---------|-------------|
| Movement | Value (Vector2) | WASD (2DVector Composite) | 事件→moveInput 字段 |
| Jump | Button | Space | 轮询 WasPressedThisFrame |
| Dash | Button | Left Shift | 轮询 WasPressedThisFrame |
| Attack | Button | 鼠标左键 | 轮询 WasPressedThisFrame / WasPerformedThisFrame |
| CounterAttack | Button | Q | 轮询 WasPressedThisFrame |
| Spell | Button | E | 事件订阅→TryUseSkill |
| RangeAttack | Button | 鼠标右键 | 轮询 WasPressedThisFrame / WasReleasedThisFrame |
| Mouse | Value (Vector2) | 鼠标位置 | 事件→mousePosition 字段 |
| UltimateSpell | Button | R | 轮询 WasPressedThisFrame |
| Interact | Button | F | 事件订阅→TryInteract |
| QuickSlot_1 | Button | 1 | 事件订阅→TryUseQuickItemInSlot(1) |
| QuickSlot_2 | Button | 2 | 事件订阅→TryUseQuickItemInSlot(2) |

**UI Action Map（6 个 Action）：**

| Action | 键盘绑定 | 用途 |
|--------|---------|------|
| OptionsUI | Escape | 切换选项菜单（暂停游戏） |
| InventoryUI | C | 切换背包界面 |
| SkillTreeUI | L | 切换技能树界面 |
| AlternativeInput | Left Ctrl | 按住时启用快捷键的"替代行为"（如快速丢弃物品） |
| DialogueInteraction | F | 对话中推进对话 |
| DialogueNevigation | W/S (1D Axis) | 对话中切换选项 |

**值得注意的细节：**

- Movement 用的是 `2DVector(mode=1)` 复合绑定——mode=1 表示 Digital Normalized，WASD 输出始终是单位向量（不会出现斜向 1.414 倍速问题）
- Attack 同时绑定到 `Mouse/leftButton`——**没有绑定键盘键**，所以不能用键盘攻击
- 只有一套 Control Scheme（"Keyborad & Mouse"，注意原作者拼写错误），没有手柄/触摸支持
- 所有 Button 类型 Action 都没设 `interactions`（没有 Hold/Tap/MultiTap 等修饰），保持最简

### 6.2 "事件订阅" vs "状态轮询" 的分界线

这是一个很容易让人困惑的设计选择。核心规则是：

> **如果所有状态都需要知道这个输入的最新值 → 用事件，存字段。如果只有特定状态需要响应这个输入 → 放状态 Update 里轮询。**

具体来说：

```csharp
// ✅ 事件订阅 —— 因为 moveInput 被几乎所有状态读取（Move/Idle/Air/Attack 驱动力方向等）
input.Player.Movement.performed += context => moveInput = context.ReadValue<Vector2>();
input.Player.Movement.canceled += ctx => moveInput = Vector2.zero;

// ✅ 事件订阅 —— mousePosition 被 SwordThrowState 用于瞄准，也可能被其他地方用
input.Player.Mouse.performed += ctx => mousePosition = ctx.ReadValue<Vector2>();

// ✅ 状态轮询 —— Attack 在不同状态有不同含义，各自决定
// 在 Player_GroundedState 里：Attack → BasicAttackState
// 在 Player_AirState 里：Attack → JumpAttackState
// 在 Player_BasicAttackState 里：Attack → comboAttackQueued（连击排队）
// 在 Player_SwordThrowState 里：Attack → 确认投掷

// ✅ 状态轮询 —— Dash 放在 PlayerState 基类，所有状态都能触发，但通过 CanDash() 做条件过滤
if (input.Player.Dash.WasPressedThisFrame() && CanDash())
```

**一个有趣的边界情况——Spell：**

```csharp
// Player.cs :215
input.Player.Spell.performed += ctx => skillManager.shard.TryUseSkill();
input.Player.Spell.performed += ctx => skillManager.timeEcho.TryUseSkill();
```

Spell 用事件订阅而不是状态轮询，因为技能的使用判定完全由 `Skill_Base.CanUseSkill()` 内部管理（冷却检查+是否已解锁），不需要依赖玩家状态机。如果 Spell 放状态里轮询，就需要在每个可能使用技能的状态里都写一遍，而这个项目几乎所有状态都可以放技能——所以事件订阅更干净。

### 6.3 WasPressedThisFrame vs WasPerformedThisFrame vs WasReleasedThisFrame

这三个是理解本项目输入处理的核心：

```csharp
// WasPressedThisFrame —— 按钮"刚按下"的那一帧返回 true
// 用于：Jump、Attack（起手）、Dash、CounterAttack
input.Player.Jump.WasPressedThisFrame()

// WasPerformedThisFrame —— 按钮完成一次完整交互（对于普通 Button 等同于按下；对于带 Hold 的会延迟触发）
// 用于：RangeAttack（进 SwordThrowState 的条件）、Attack（在 SwordThrow 中确认投掷）
input.Player.Attack.WasPerformedThisFrame()
input.Player.RangeAttack.WasPerformedThisFrame()

// WasReleasedThisFrame —— 按钮"刚松开"的那一帧返回 true
// 用于：SwordThrow 中取消投掷
input.Player.RangeAttack.WasReleasedThisFrame()
```

**为什么 RangeAttack 进入 SwordThrow 用 `WasPerformedThisFrame`，取消用 `WasReleasedThisFrame`？**

这实现了一个"按住瞄准→松开取消"的交互模式。`WasPerformedThisFrame` 确保只在按下那帧进入状态（不会重复进入），然后在状态里持续显示瞄准轨迹，`WasReleasedThisFrame` 检测松手=取消。这比用 `IsPressed()` 轮询更省心——你不需要额外维护一个 `wasHoldingLastFrame` 的标志位。

### 6.4 Input Action Map 的 Enable/Disable 生命周期

本项目手动管理 Action Map 的开关，没有用 `PlayerInput` 组件的自动切换：

```
启动流程：
  Awake → new PlayerInputSet() → input.Player 和 input.UI 都未启用
  OnEnable → input.Enable() → 两个 Map 同时启用

UI 打开：
  StopPlayerControls(true) → input.Player.Disable() → 游戏操作被屏蔽
  （UI Map 保持启用，UI 按键仍然响应）

UI 关闭：
  StopPlayerControls(false) → input.Player.Enable() → 恢复游戏操作

对象销毁/禁用：
  OnDisable → input.Disable() → 完全禁用
```

**这里有个隐式规则**：`input.Enable()` 启用的是整个 asset（两个 Map 都启用），但通过 `input.Player.Disable()` 单独禁用 Player Map 来隔离 UI。UI Map 始终处于启用状态，因为 `input.Enable()` 之后从未单独禁用它。

**一个潜在的坑：** `PlayerInputSet` 没有调用 `Dispose()`。查看析构函数：

```csharp
// PlayerInputSet.cs :577-581
~@PlayerInputSet()
{
    UnityEngine.Debug.Assert(!m_Player.enabled, "This will cause a leak...");
    UnityEngine.Debug.Assert(!m_UI.enabled, "This will cause a leak...");
}
```

析构函数只 Assert，不自动清理。不过因为这个项目中 `PlayerInputSet` 的生命周期跟 Player 一致，且 Player 不会被销毁，所以实际上不会触发。但如果以后做场景切换，Player 被 Destroy 时，需要手动调用 `input.Dispose()`。

### 6.5 连击排队的输入处理

`Player_BasicAttackState` 的输入处理是本项目输入系统最精妙的部分：

```csharp
// Player_BasicAttackState.cs :40-41
public override void Update()
{
    base.Update();
    HandleAttackVelocity();
    if (input.Player.Attack.WasPressedThisFrame())
        QueueNextAttack();    // ← 只设置标志位，不立刻切换状态

    if (triggerCalled)
        HandleStateExit();    // ← 动画播放完（Animation Event 触发）才处理
}
```

而 `QueueNextAttack()` 只做了一件事：

```csharp
// :85-88
private void QueueNextAttack()
{
    if (comboIndex < comboLimit)
        comboAttackQueued = true;
}
```

然后当动画播放到最后一帧，Animation Event 调用 `Entity_AnimationTriggers → EntityState.AnimationTrigger()` 把 `triggerCalled` 设为 true，此时 `HandleStateExit()` 才决定：连击已排队→延迟一帧进入下一击，否则→回 Idle。

**这个设计解决了一个经典问题：** 如果攻击动画中检测到 Attack 按下的瞬间立刻切换状态，下一击的动画会在当前动画还没播完时就开始，导致动画跳帧。解决方案是"排队"——记录玩家想连击的意图，等当前动画自然播完后再执行。

但还有一个更微妙的处理：

```csharp
// Player.cs :160-173
public void EnterAttaclStateWithDelay()
{
    if (queueAttackCo != null)
        StopCoroutine(queueAttackCo);
    queueAttackCo = StartCoroutine(EnterAttackStateWithDelayCo());
}

private IEnumerator EnterAttackStateWithDelayCo()
{
    yield return new WaitForEndOfFrame();  // ← 延迟一帧！
    stateMachine.ChangeState(basicAttackState);
}
```

**为什么连击也要延迟一帧？** 因为在动画最后一帧，`triggerCalled` 触发 → `HandleStateExit()` → `anim.SetBool(animBoolName, false)` 关闭动画参数 → 同一帧内 Animator 还没来得及处理。如果立刻 `ChangeState`，新状态的 `Enter()` 会设置 `anim.SetBool(animBoolName, true)`，但当前帧 Animator 可能先看到 false 再看到 true，导致过渡异常。延迟一帧确保 Animator 先处理完退出再处理进入。

### 6.6 Dash 的输入处理——多条件过滤

```csharp
// PlayerState.cs :56-68
private bool CanDash()
{
    if (skillManager.dash.CanUseSkill() == false)   // 技能未解锁或在冷却
        return false;
    if (player.wallDetected)                          // 贴墙不能 Dash
        return false;
    if (stateMachine.currentSate == player.dashState  // 已经在 Dash 中
        || stateMachine.currentSate == player.domainExpansionState)  // 领域展开中
        return false;
    return DashCDCalculate();   // 冷却时间检查
}
```

Dash 的输入检测放在 `PlayerState` 基类（所有状态的公共逻辑），但通过 `CanDash()` 做了五层条件过滤。这比在每个子类状态中重复判断要干净得多。

## 7. 与 Unity 自带方案的对比

| 方面 | Unity 内置方案 | 本项目实际做法 | 评价 |
|------|--------------|-------------|------|
| PlayerInput 组件 | 拖拽赋值，Inspector 配置 | **不用**，手动 `new PlayerInputSet()` | 更灵活，可以在代码中完全控制生命周期 |
| SendMessage/Broadcast | 组件自动调用 `OnJump()` 等方法 | **不用**，直接订阅 C# 事件或轮询 | 避免了字符串反射的性能损失和重构风险 |
| InputActionMap 自动切换 | PlayerInput 根据 Control Scheme 自动切换 | **手动**管理 `input.Player.Enable()/Disable()` | 虽然多了几行代码，但和 UI 面板的联动更透明可控 |
| C# 事件回调接口 | `AddCallbacks(IPlayerActions)` | **不用**生成的接口，自己写 lambda 订阅 | 更灵活，不需要一个类实现所有 12 个回调方法 |

**补充说明：** 生成的 `PlayerInputSet` 提供了 `IPlayerActions` 接口和 `AddCallbacks/RemoveCallbacks` 方法，但项目没有使用它们。项目选择了更灵活的方式：在 `Player.OnEnable` 中用 lambda 表达式按需订阅，在 `UI.SetupControlsUI` 中也是直接 lambda。

```csharp
// 1. 持续型输入：事件驱动，存字段
// Player.cs
input.Player.Movement.performed += ctx => moveInput = ctx.ReadValue<Vector2>();

// 2. 离散型输入：状态轮询，各状态独立处理

if (input.Player.Jump.WasPressedThisFrame())

if (input.Player.Attack.WasPressedThisFrame())

// 1. 按键映射全在 .inputactions 文件中，改键只需改 JSON 或编辑器拖拽

```

## 9. 易混淆点 FAQ

### Q1: 为什么有两种 `.inputactions` 文件？哪个是实际用的？

`InputSystem_Actions.inputactions` 是 Unity 的默认模板（包含 Player+UI 两个 Map，支持键盘/手柄/触摸/XR 多设备），`PlayInputSet.inputactions` 是项目自定义的游戏实际绑定。代码中只有 `PlayerInputSet.cs` 对应 `PlayInputSet.inputactions`。前者可能是一开始创建的模板，后来被替换了但没删。

### Q2: `WasPressedThisFrame` 和 `WasPerformedThisFrame` 有什么区别？

对于没有设置 `interactions` 的普通 Button Action，两者行为相同——都在按下的第一帧返回 true。但如果 Action 配置了 `Hold`（如 `InputSystem_Actions` 里的 Interact 就绑了 Hold），`WasPressedThisFrame` 仍然在按下瞬间返回 true，而 `WasPerformedThisFrame` 要等 Hold 时间满足后才返回 true。

### Q3: 为什么 Spell 用事件订阅，而 Attack 用状态轮询？

Spell 的使用判定依赖 `Skill_Base.CanUseSkill()`（冷却+解锁检查），与玩家处于什么状态无关——Idle、Move、Jump、甚至某些攻击后摇中都能放技能。如果放在状态轮询里，每个允许放技能的状态都要写一遍 `Spell.WasPressedThisFrame()`，而事件订阅只需要一行。Attack 则不同——它在不同状态有完全不同的行为，必须分散到各状态中。

### Q4: 为什么不在 `Player_BasicAttackState` 里也检测 CounterAttack？

代码里有一行被注释掉的：

```csharp
// Player_BasicAttackState.cs :47-48
//if (input.Player.CounterAttack.WasPressedThisFrame())
//    stateMachine.ChangeState(player.counterAttackState);
```

可能的原因：攻击动画播放中允许反击会导致动画混合问题。反击需要播放格挡动画，如果当前正在播放攻击动画，两个动画的过渡会很生硬。课程作者可能测试后认为这不合适。

### Q5: Movement 事件的 `canceled` 回调为什么设为 `Vector2.zero` 而不是保持最后值？

因为 2D 游戏的移动方向是离散控制（WASD 而不是摇杆），松开所有键时方向应该归零让角色立刻停下。如果保持最后值，角色会永远朝最后按的方向走。

### Q6: `AlternativeInput` 是做什么的？

在 UI 中按住 Left Ctrl 时，`alternativeInput` 标志为 true。查看代码可以推断它用于快捷键的"替代行为"——比如在背包中点击物品是"装备"，按住 Ctrl 点击可能是"快速丢弃"。这是一个省按键的设计。

### Q7: 为什么析构函数里只有 Assert 而不是自动清理？

```csharp
~@PlayerInputSet()
{
    UnityEngine.Debug.Assert(!m_Player.enabled, "...");
}
```

这是 Unity 生成代码的标准做法——析构函数中做清理可能因为 GC 调用顺序不确定而出问题，所以只做断言提示。实际清理应该由使用者调用 `Dispose()`。

### Q8: `player.moveInput` 和 `player.mousePosition` 的类型分别是什么？

```csharp
// Player.cs :68-69
public Vector2 moveInput { get; private set; }
public Vector2 mousePosition { get; private set; }
```

都是 `Vector2`。`moveInput` 来自 WASD 的 2DVector 复合绑定（值是 `(±1, ±1)` 范围），`mousePosition` 来自 `Mouse/position` 的屏幕像素坐标（需要 `Camera.ScreenToWorldPoint()` 转换成世界坐标）。

## 10. 如何迁移到自己的项目

### 可直接复用的

- **`PlayerInputSet.cs` 的生成流程**：创建 `.inputactions` 资源 → 勾选 "Generate C# Class" → 得到一个强类型包装类
- **"持续型用事件，离散型用状态轮询"的划分策略**：适用于几乎所有基于状态机的动作游戏
- **`ActionMap.Disable()/Enable()` 做 UI 隔离**：比在代码里到处写 `if (uiOpen) return;` 优雅得多

### 需要改造的

- **Action 命名**：根据你自己的游戏重新定义（Attack/Jump/Dash 等）
- **按键绑定**：本项目只有键盘+鼠标，你需要加上手柄（在 `.inputactions` 里添加 Gamepad 的 binding）
- **input 的生命周期管理**：如果角色会销毁重建，记得调用 `input.Dispose()`

### 迁移后最容易出的错

1. **忘了 `.inputactions` 文件里的 "Generate C# Class" 勾选框** → 代码里找不到 `PlayerInputSet`。要点：选中 `.inputactions` → Inspector → 勾选 "Generate C# Class" → Apply
2. **Action 名改了但代码里还在用旧名** → 编译报错。好在生成的是强类型属性，改名后编译期就能发现，比旧 Input 系统的字符串魔法值安全
3. **ActionMap 的 Enable/Disable 顺序**：如果两个 Map 有同名 Action（比如 Player 和 UI 都有 "Click"），后 Enable 的会覆盖先 Enable 的。本项目 Player 和 UI 没有重叠 Action，所以没问题

## 11. 优化建议

### 本项目可以改进的地方

1. **`PlayerInputSet` 缺少 `Dispose()` 调用**：在 `Player.OnDestroy()` 中应该调用 `input.Dispose()` 释放 InputActionAsset 的内部资源。虽然 Player 是持久对象，但作为好习惯应该加上。

2. **硬编码按键键值**：`PlayInputSet.inputactions` 中只有一套 "Keyborad & Mouse" 的 Control Scheme，不支持手柄。加 Gamepad binding 不影响现有键盘逻辑，一行 C# 代码都不用改。

3. **`UI.cs` 的 `alternativeInput` 标志**：用 `performed/canceled` 事件配合 lambda 设置 bool 标志，这是典型的"把 Button 当 Value 用"模式。其实可以直接在需要判断的地方写 `input.UI.AlternativeInput.IsPressed()`，省掉一个字段。

4. **缺少输入重绑定（Rebinding）支持**：`.inputactions` 的按键是写死在 JSON 里的，玩家不能在游戏内改键。正式项目需要加上运行时重新绑定功能（新输入系统的 `InputActionRebindingExtensions` 提供了完整 API）。

## 12. 总结

**系统本质：** 这是一个基于 Unity New Input System 的"轻量级封装"——用一个生成的 C# 包装类 `PlayerInputSet` 替代 `PlayerInput` 组件，通过"事件驱动（持续型输入）+ 状态轮询（离散型输入）"的混合模式，将语义化的游戏动作精准分发到状态机的各个状态中。

**最重要的三个类：**
- `PlayerInputSet`：生成的强类型包装，封装了所有 Action 的查找和生命周期
- `Player`：创建 InputSet、管理 Enable/Disable、将 Movement/Mouse 转为字段供所有状态读取
- `PlayerState`：各状态的基类，在 `Update()` 中通过 `WasPressedThisFrame()` 轮询输入实现状态切换

**核心流程：** `.inputactions`（JSON）→ `PlayerInputSet`（生成代码）→ `Player.OnEnable` 订阅事件 → `PlayerState.Update` 轮询 → 状态切换

**最该学到什么：**
- 同一个 Attack 按钮在不同状态做不同的事——这是状态机+输入系统配合的精华
- 用 `ActionMap.Enable()/Disable()` 做 UI 隔离比代码里 if-else 干净得多
- `WasPressedThisFrame` / `WasPerformedThisFrame` / `WasReleasedThisFrame` 三个 API 的选择决定了交互手感
- 生成 C# 类用强类型属性访问 Action 避免了旧系统的字符串魔法值问题

# 技能系统深度分析_主程讲解版

> 分析对象：`Udemy-Course-RPG` 的技能系统  
> 重点阅读顺序：先看第 2、3 节建立整体模型，再看第 5 节运行流程，最后看第 8、9 节理解 Unity 配置和容易踩的坑。

## 1. 系统定位：这个技能系统解决什么问题？

这个项目的技能系统不是一个简单的“按键 -> 生成特效 -> 扣血”脚本，而是一套把 **技能配置、技能树解锁、玩家输入、状态机、场上技能物体、伤害结算、UI 冷却、存档** 串起来的玩法框架。

它解决的核心问题有四个：

| 问题 | 项目里的做法 |
| --- | --- |
| 技能数据怎么配 | 用 `Skill_DataSO` 存名字、描述、图标、花费、技能类型、升级类型、冷却和伤害倍率 |
| 玩家怎么解锁技能 | 用 `UI_TreeNode` 表示技能树节点，节点检查前置、互斥、技能点，解锁后把 SO 数据注入具体技能 |
| 技能怎么释放 | 通过 `PlayerState`、`Player_GroundedState`、`Player_SwordThrowState`、`Player_DomainExpansionState` 和输入系统触发 |
| 技能怎么落地 | 每个技能有一个 `Skill_*` 管理类，真正飞出去、爆炸、攻击、减速的东西是 `SkillObject_*` prefab |

最重要的一句话是：

**这个技能系统的本质是：ScriptableObject 做配置，UI 技能树做解锁路由，`Skill_Base` 做运行时技能槽，`SkillObject_*` 做场上表现和伤害。**

这套拆法很适合课程项目，因为它让“新增一个技能升级”不一定要改玩家主脚本。比如冲刺产生分身、冲刺产生碎片、飞剑变成旋转剑，本质上都是换 `SkillUpgradeType` 后走不同分支。

## 3. 分层设计

### 3.1 数据层：Skill_DataSO

`Skill_DataSO` 是整个系统的“设计表”。每个技能树节点都拖一个 `.asset`，而不是在 UI 节点上手写技能参数。

核心字段在 `Assets/Scripts/Data/Skill_DataSO.cs:7`：

```csharp
public string displayName;
public string description;
public Sprite icon;
public int cost;
public bool unlockedByDefault;
public SkillType skillType;
public UpagradeData upagradeData;
```

`UpagradeData` 里放真正影响运行时的三件事：

```csharp
public SkillUpgradeType upgradeType;
public float cooldown;
public DamageScaleData damageScaleData;
```

这说明项目把技能数据分成两类：

| 数据 | 用途 |
| --- | --- |
| `displayName`, `description`, `icon`, `cost` | UI 展示和解锁成本 |
| `skillType`, `upgradeType`, `cooldown`, `damageScaleData` | 运行时技能逻辑 |

为什么这样设计比较好？

如果把冷却、伤害倍率、图标都写在技能脚本里，策划想改 “Quick dash” 的冷却就要改代码。现在这些数据在 `Assets/Data/Skill data` 下面的资产里，例如：

- `Quick dash` 是默认解锁，`skillType: 0`，`upgradeType: 1`，`cooldown: 3`：`Assets/Data/Skill data/Skill data - Dash/Skill data - Quick dash.asset:20`
- `Time shard` 是时间碎片基础分支，`cooldown: 1`，物理和元素倍率都是 1：`Assets/Data/Skill data/Skill data - Time shard/Skill data - Time shard.asset:21`
- `Catch this` 是普通飞剑，`skillType: 3`，`upgradeType: 11`，`cooldown: 2`：`Assets/Data/Skill data/Skill data - Sword throw/Skill data - Catch this!.asset:18`

这里的代价是：`SkillUpgradeType` enum 的顺序一旦变了，Unity asset 里保存的数字就可能对不上。所以 enum 已经被资产引用后，不要随便在中间插值，最好只在末尾追加。

### 3.2 运行时技能槽：Skill_Base

`Skill_Base` 是所有技能的共同运行时壳子，负责三类共性：

| 职责 | 代码位置 |
| --- | --- |
| 找到玩家和技能管理器 | `Assets/Scripts/SkillSystem/Skill_Base.cs:17` |
| 接收技能树注入的升级数据 | `Assets/Scripts/SkillSystem/Skill_Base.cs:31` |
| 统一判断解锁和冷却 | `Assets/Scripts/SkillSystem/Skill_Base.cs:54` |

关键方法是 `SetSkillUpgrade()`：

```csharp
UpagradeData upgrade = skillData.upagradeData;
this.upgradeType = upgrade.upgradeType;
this.cooldown = upgrade.cooldown;
damageScaleData = upgrade.damageScaleData;
player.ui.inGameUI.GetSkillSlot(skillType).SetupSkillSlot(skillData);
ReSetCooldown();
```

注意这个方法做了两件很聪明的事：

1. 把 SO 数据复制到运行时技能对象里。
2. 顺手更新游戏内技能栏图标和冷却 UI。

也就是说，技能树不是直接释放技能。技能树只负责“把当前技能槽换成某个升级版本”。真正释放时，各个技能脚本只看自己的 `upgradeType`。

冷却逻辑也集中在基类：

- `CanUseSkill()` 先挡掉 `SkillUpgradeType.None`：`Assets/Scripts/SkillSystem/Skill_Base.cs:54`
- `OnCooldown()` 用 `Time.time < lastTimeUsed + cooldown` 判断：`Assets/Scripts/SkillSystem/Skill_Base.cs:73`
- `SetSkillOnCooldown()` 同时启动 UI 冷却遮罩：`Assets/Scripts/SkillSystem/Skill_Base.cs:74`
- `ReduceCooldownBy()` 通过修改 `lastTimeUsed` 实现全技能减冷却：`Assets/Scripts/SkillSystem/Skill_Base.cs:80`

这个设计比每个技能自己写一套冷却靠谱很多，因为 UI、冷却、解锁判断不会散落在五个技能脚本里。

### 3.3 技能管理层：Player_SkillManager

`Player_SkillManager` 是玩家身上的技能目录。

```csharp
dash = GetComponentInChildren<Skill_Dash>();
shard = GetComponentInChildren<Skill_Shard>();
swordThrow = GetComponentInChildren<Skill_SwordThrow>();
timeEcho = GetComponentInChildren<Skill_TimeEcho>();
domainExpansion = GetComponentInChildren<Skill_DomainExpansion>();
allSkills = GetComponentsInChildren<Skill_Base>();
```

代码位置：`Assets/Scripts/Player/Player_SkillManager.cs:13`

它的职责不是写技能逻辑，而是做路由：

| 方法 | 作用 |
| --- | --- |
| `GetSkillByType(SkillType type)` | 技能树根据 SO 的 `skillType` 找到正确技能槽 |
| `ReduceAllSkillCooldownBy(float amount)` | Time Echo 的冷却精灵统一减少所有技能 CD |
| `WashAllSkills()` | 把所有技能升级重置成 `None` |

`GetSkillByType()` 的 switch 是这个系统的一个中心路口：`Assets/Scripts/Player/Player_SkillManager.cs:32`

```text
Dash            -> Skill_Dash
TimeShard       -> Skill_Shard
SwordThrow      -> Skill_SwordThrow
TimeEcho        -> Skill_TimeEcho
DomainExpansion -> Skill_DomainExpansion
```

好处是 UI 不需要知道 `Skill_Shard` 这个类名，它只认识 `SkillType.TimeShard`。坏处是新增大类技能时要改 enum 和这个 switch。

### 3.4 表现层：SkillObject_*

`Skill_*` 是“技能控制器”，`SkillObject_*` 是“技能实体”。

这是非常关键的拆分。比如时间碎片：

- `Skill_Shard` 知道玩家当前解锁了哪种碎片、冷却是多少、能不能多重施法。
- `SkillObject_Shard` 才是真正在场景中移动、碰撞、爆炸、销毁的 GameObject。

飞剑也是同理：

- `Skill_SwordThrow` 负责选择 prefab、预测轨迹、记录方向。
- `SkillObject_Sword` 和子类负责飞行、命中、回收、旋转、穿透、弹射。

如果不拆，玩家身上的技能脚本会同时承担输入、冷却、生成、碰撞、伤害、销毁，后期一定会膨胀。

## 5. 运行流程：从打开游戏到释放技能

### 5.1 初始化流程

```text
Player.Awake()
  -> GetComponent<Player_SkillManager>()
  -> new PlayerInputSet()
  -> ui.SetupControlsUI(input)
  -> 创建各种 PlayerState

Player_SkillManager.Awake()
  -> GetComponentInChildren<Skill_Dash / Skill_Shard / ...>
  -> allSkills = GetComponentsInChildren<Skill_Base>()

UI.Start()
  -> skillTreeUI.UnlockDefaultSkills()

UI_SkillTree.UnlockDefaultSkills()
  -> allTreeNodes = GetComponentsInChildren<UI_TreeNode>(true)
  -> skillManager = FindAnyObjectByType<Player_SkillManager>()
  -> 每个 node.UnlockedDefaultSkill()

UI_TreeNode.UnlockedDefaultSkill()
  -> 如果 skillData.unlockedByDefault
  -> Unlock()
  -> Skill_Base.SetSkillUpgrade(skillData)
```

关键代码：

- Player 缓存 `Player_SkillManager`：`Assets/Scripts/Player/Player.cs:77`
- UI 在 Start 解锁默认技能：`Assets/Scripts/UI/UI.cs:54`
- 技能树收集所有节点和技能管理器：`Assets/Scripts/UI/SkillTreeUI/UI_SkillTree.cs:24`

这个初始化顺序很重要。技能树节点需要 `Player_SkillManager` 已经存在，否则无法把默认技能注入玩家技能槽。

### 5.2 解锁流程

玩家点击技能树节点时：

```text
UI_TreeNode.OnPointerDown()
  -> CanBeUnlocked()
      -> 不是 locked
      -> 不是 unlocked
      -> 技能点足够
      -> needNodes 都已解锁
      -> conflictNodes 都未解锁
  -> Unlock()
      -> isUnlocked = true
      -> 图标变白
      -> LockConflictNodes()
      -> skillTree.RemoveSkillPoints(cost)
      -> connectHandler.UnlockConnectionImage(true)
      -> skillManager.GetSkillByType(skillData.skillType).SetSkillUpgrade(skillData)
```

代码位置：

- 点击入口：`Assets/Scripts/UI/SkillTreeUI/UI_TreeNode.cs:151`
- 条件检查：`Assets/Scripts/UI/SkillTreeUI/UI_TreeNode.cs:97`
- 解锁实现：`Assets/Scripts/UI/SkillTreeUI/UI_TreeNode.cs:70`
- 互斥分支锁定：`Assets/Scripts/UI/SkillTreeUI/UI_TreeNode.cs:123`

这里最有设计价值的是 `needNodes` 和 `conflictNodes` 都是 Inspector 配置的数组。也就是说技能树结构主要由 Unity 编辑器搭出来，代码只提供通用规则。

初学者很容易把技能树写成一堆 if：

```text
if (clickDashClone && dashUnlocked && points >= 2) ...
if (clickDashShard && dashUnlocked && !cloneUnlocked) ...
```

这样节点一多就炸。项目现在的写法把“前置”和“互斥”变成节点自己的数据，代码不用知道具体哪条线接哪条线。

### 5.3 释放流程总览

不同技能有不同入口：

| 技能 | 输入 / 状态入口 | 释放方式 |
| --- | --- | --- |
| Dash | `PlayerState.Update()` 检查 Dash 输入 | 直接切到 `Player_DashState` |
| TimeShard | `Player.OnEnable()` 订阅 Spell | 直接 `skillManager.shard.TryUseSkill()` |
| TimeEcho | `Player.OnEnable()` 订阅 Spell | 直接 `skillManager.timeEcho.TryUseSkill()` |
| SwordThrow | `Player_GroundedState.Update()` 检查 RangeAttack | 进入瞄准状态，动画事件生成飞剑 |
| DomainExpansion | `PlayerState.Update()` 检查 UltimateSpell | 普通领域立刻创建，施法领域进入悬浮状态 |

代码证据：

- Dash 和大招输入在所有 PlayerState 的公共 Update 中处理：`Assets/Scripts/StateMachine/PlayerState.cs:22`
- Spell 同时触发碎片和时间回声：`Assets/Scripts/Player/Player.cs:215`
- 地面状态进入飞剑瞄准：`Assets/Scripts/Player/PlayerStates/Player_GroundedState.cs:31`
- 飞剑动画事件调用 `ThrowSword()`：`Assets/Scripts/Player/Player_AnimationTriggers.cs:12`
- PlayerThrowSword_performed 动画事件包含 `ThrowSword`：`Assets/Animations/Player/PlayerThrowSword_performed.anim:90`

这里有一个课程项目常见的“输入复用”设计：`Spell` 一个键同时触发 `shard.TryUseSkill()` 和 `timeEcho.TryUseSkill()`。实际能不能释放由各自的 `CanUseSkill()` 和 `upgradeType` 决定。只要其中一个技能没解锁，它会在基类里返回 false。

## 6. 五个技能大类详解

### 6.1 Dash：冲刺技能是“状态机主导 + 技能升级挂效果”

Dash 本身不是 `Skill_Dash.TryUseSkill()` 驱动的，而是玩家状态机驱动。

流程：

```text
PlayerState.Update()
  -> input.Player.Dash.WasPressedThisFrame()
  -> CanDash()
      -> skillManager.dash.CanUseSkill()
      -> 不在墙上
      -> 不在 dash/domain 状态
      -> 玩家 dashCoolDown 到期
  -> skillManager.dash.SetSkillOnCooldown()
  -> stateMachine.ChangeState(player.dashState)

Player_DashState.Enter()
  -> skillManager.dash.OnStartEffect()
  -> player.vfx.DoImageEchoEffect(player.dashDuration)
  -> gravityScale = 0
  -> 玩家无敌 + layer 切到 Untargetable

Player_DashState.Exit()
  -> skillManager.dash.OnEndEffect()
  -> 恢复速度 / 重力 / 受击 / layer
```

关键代码：

- Dash 输入和冷却：`Assets/Scripts/StateMachine/PlayerState.cs:29`
- Dash 状态进入时触发开始效果：`Assets/Scripts/Player/PlayerStates/Player_DashState.cs:15`
- Dash 状态退出时触发结束效果：`Assets/Scripts/Player/PlayerStates/Player_DashState.cs:49`
- Dash 升级效果判断：`Assets/Scripts/SkillSystem/Skill_Dash.cs:15`

`Skill_Dash` 的设计点在于：它不负责移动，不负责无敌，不负责状态切换。它只负责“冲刺开始/结束时附带什么技能效果”。

```csharp
if (Unlocked(SkillUpgradeType.Dash_CloneOnStart) ||
    Unlocked(SkillUpgradeType.Dash_CloneOnStartAndArrival))
    CreateClone();

if (Unlocked(SkillUpgradeType.Dash_ShardOnStart) ||
    Unlocked(SkillUpgradeType.Dash_ShardOnStartAndArrival))
    CreateShard();
```

这个分工很清楚：

| 模块 | 负责内容 |
| --- | --- |
| `Player_DashState` | 位移、无敌、重力、状态切换 |
| `Skill_Dash` | 根据升级类型在冲刺前后生成分身或碎片 |
| `Skill_TimeEcho` | 真正创建时间回声 |
| `Skill_Shard` | 真正创建时间碎片 |

为什么不把分身和碎片写死在 DashState？因为 DashState 是移动状态，技能分支是成长系统。两者变化原因不同，拆开以后更稳。

### 6.2 Time Shard：时间碎片是“同一技能槽，多种行为分支”

`Skill_Shard.TryUseSkill()` 根据 `upgradeType` 分发到五种玩法：`Assets/Scripts/SkillSystem/Skill_Shard.cs:58`

| 升级 | 行为 |
| --- | --- |
| `Shard` | 原地生成碎片，延迟爆炸 |
| `Shard_MoveToEnemy` | 生成后追踪最近敌人 |
| `Shard_MultiCast` | 3 次充能，逐个恢复 |
| `Shard_Teleport` | 第一次放碎片，第二次和碎片换位 |
| `Shard_TeleportHpRewind` | 换位同时把血量回到释放碎片时的百分比 |

普通碎片流程：

```text
Skill_Shard.TryUseSkill()
  -> CanUseSkill()
  -> HandleShardRegular()
  -> CreateShard()
  -> Instantiate(shardPrefab)
  -> SkillObject_Shard.SetupShard(this)
  -> Invoke(Explode, detonationTime)
  -> SetSkillOnCooldown()

SkillObject_Shard.Explode()
  -> DamageEnemiesInRadius(transform, checkRadius)
  -> Instantiate(vfxPrefab)
  -> VFX 按 usedElement 染色
  -> OnExplode?.Invoke()
  -> Destroy(gameObject)
```

关键代码：

- 碎片 prefab 字段：`Assets/Scripts/SkillSystem/Skill_Shard.cs:10`
- 创建碎片：`Assets/Scripts/SkillSystem/Skill_Shard.cs:34`
- 追踪碎片：`Assets/Scripts/SkillSystem/Skill_Shard.cs:145`
- 多重施法充能协程：`Assets/Scripts/SkillSystem/Skill_Shard.cs:133`
- 传送换位：`Assets/Scripts/SkillSystem/Skill_Shard.cs:106`
- 血量回溯：`Assets/Scripts/SkillSystem/Skill_Shard.cs:77`
- 碎片爆炸：`Assets/Scripts/SkillSystem/SkillObject_Shard.cs:68`

这个技能的设计很典型：**一个技能槽里只保存当前选择的升级类型，释放时按 upgradeType 走不同策略。**

优点是数据结构简单。代价是 `Skill_Shard.TryUseSkill()` 会随着分支增多变胖。如果后面继续加十几个碎片升级，适合改成“每个升级一个策略类”，但现在这个项目规模下 switch/if 分支是合理的。

传送分支有一个细节很聪明：如果玩家放了传送碎片但一直不二次触发，碎片爆炸时也要强制进入冷却。

```csharp
if (Unlocked(SkillUpgradeType.Shard_Teleport) ||
    Unlocked(SkillUpgradeType.Shard_TeleportHpRewind))
    currentShard.OnExplode += ForceCooldown;
```

代码位置：`Assets/Scripts/SkillSystem/Skill_Shard.cs:41`

## 7. 伤害与元素：技能物体如何接入战斗系统

技能物体没有复用 `Entity_Combat`，而是在 `SkillObject_Base` 里单独实现了一套范围伤害：

```csharp
foreach (var target in GetEnemiesAround(t, radius))
{
    IDamagable damagable = target.GetComponent<IDamagable>();
    AttackData attackData = playerStats.GetAttackData(damageScaleData);
    Entity_StatusHandler statusHandler = target.GetComponent<Entity_StatusHandler>();

    float phsiDamage = playerStats.GetPhyiscalDamage(out bool isCrit, damageScaleData.phsycal);
    float elemDamage = playerStats.GetElementDamage(out ElementType element, damageScaleData.elemental);

    targetGotHit = damagable.TakeDamage(phsiDamage, elemDamage, element, transform);
    if (element != ElementType.None)
        statusHandler.ApplyStausEffect(element, attackData.effectData);
}
```

代码位置：`Assets/Scripts/SkillSystem/SkillObject_Base.cs:36`

这说明技能伤害仍然吃玩家属性：

- `playerStats` 来自释放技能的玩家。
- `damageScaleData` 来自当前解锁的 `Skill_DataSO`。
- 物理伤害和元素伤害都调用 `Entity_Stats`。
- 命中目标通过 `IDamagable` 解耦。
- 元素状态通过 `Entity_StatusHandler` 应用。

这个设计的好处是：技能不会绕过战斗系统。装备、属性、暴击、元素效果都能自然影响技能。

但这里也有一个小风险：`SkillObject_Base` 同时生成了 `AttackData`，又单独调用 `GetPhyiscalDamage()` 和 `GetElementDamage()`。如果 `AttackData` 构造里已经随机了一次暴击/元素，这里又随机一次，可能造成“状态效果和实际伤害元素不一致”的潜在问题。后续优化时，可以考虑只生成一次 `AttackData`，然后所有伤害和状态都从这个快照读。

## 10. 正面例子 vs 反面例子

### 反面：把所有技能写在 Player.Update()

初学者很容易这样写：

```csharp
void Update()
{
    if (Input.GetKeyDown(KeyCode.Q))
    {
        if (hasDashClone)
            Instantiate(clonePrefab);
        if (hasDashShard)
            Instantiate(shardPrefab);
        cooldownQ = 3;
    }

    if (Input.GetKeyDown(KeyCode.E))
    {
        if (hasSwordSpin)
            Instantiate(spinSwordPrefab);
        else if (hasSwordPierce)
            Instantiate(pierceSwordPrefab);
    }
}
```

问题是：

- 输入、技能成长、冷却、生成、伤害、UI 全混在一起。
- 新增一个技能升级就要改 Player。
- UI 技能树无法自然接入。
- 存档不知道该保存哪些布尔值。

### 正面：项目实际做法

项目的链路是：

```text
Skill_DataSO 配置升级
  -> UI_TreeNode 解锁
  -> Skill_Base.SetSkillUpgrade()
  -> 当前 Skill_* 按 upgradeType 分支
  -> SkillObject_* prefab 执行表现
  -> SkillObject_Base 统一伤害
```

它的好处是每层只关心自己的事：

- SO 只关心数据。
- UI 节点只关心能不能解锁。
- 技能槽只关心当前升级和冷却。
- 状态机只关心玩家动作过程。
- 技能物体只关心在场景中怎么飞、怎么撞、怎么销毁。

这就是架构里常说的“变化原因分离”。技能数值变，改 SO；技能树关系变，改 Inspector；飞剑行为变，改飞剑 prefab 或飞剑子类；玩家冲刺手感变，改 DashState。

## 11. 容易混淆的点 FAQ

### Q1：`SkillType` 和 `SkillUpgradeType` 有什么区别？

`SkillType` 是技能大类，比如 Dash、TimeShard、SwordThrow。  
`SkillUpgradeType` 是这个大类下的具体版本，比如 Dash_CloneOnStart、Shard_Teleport、SwordThrow_Bounce。

一句话：`SkillType` 决定找哪个技能槽，`SkillUpgradeType` 决定这个技能槽现在怎么表现。

### Q2：为什么 `Skill_DataSO` 不直接释放技能？

SO 是资产数据，不应该持有场景对象生命周期。真正释放技能需要玩家、位置、属性、UI、输入状态，这些都属于运行时对象。所以 SO 只提供参数，`Skill_Base` 和子类负责运行时逻辑。

### Q3：为什么飞剑要先进 `Player_SwordThrowState`？

因为飞剑需要瞄准、显示轨迹、确认方向、等待动画出手帧。直接按键生成会少掉“蓄势/瞄准/出手同步”这几个动作游戏手感关键环节。

### Q4：为什么 TimeShard 和 TimeEcho 用同一个 Spell 输入？

根据代码，`Player.OnEnable()` 同时订阅了两个回调：`Assets/Scripts/Player/Player.cs:215`。实际哪个能释放由 `CanUseSkill()` 和 `upgradeType` 决定。这样做简化输入配置，但如果未来两个技能都解锁且都不在 CD，按一次 Spell 可能会同时尝试释放两个技能。是否符合设计要看课程目标。

### Q5：技能物体的伤害为什么不直接写在每个子类里？

因为碎片、飞剑、回声都需要“找范围内敌人、读取玩家属性、计算物理/元素伤害、应用状态、生成命中特效”。这些共性放在 `SkillObject_Base.DamageEnemiesInRadius()`，子类只负责什么时候调用它。

### Q6：领域为什么要分 instant 和非 instant？

减速领域可以立刻放，因为它只是一个区域效果。召唤碎片/回声的领域需要玩家进入特殊表演状态，悬浮一段时间并持续施法，所以进入 `Player_DomainExpansionState`。

### Q7：技能树存档为什么既保存节点，又保存升级类型？

节点 bool 用来恢复 UI；升级类型用来恢复运行时技能槽。只保存其中一个都不完整。

### Q8：为什么冲刺技能没有重写 `TryUseSkill()`？

Dash 是移动状态，不是普通即时技能。它的释放由 `PlayerState.Update()` 统一检查 Dash 输入，然后切换到 `Player_DashState`。`Skill_Dash` 只挂接冲刺开始和结束时的附加效果。

## 12. 当前实现的优点

### 12.1 数据和逻辑分离

`Skill_DataSO` 让技能名字、描述、图标、花费、冷却、伤害倍率都可配置。代码不用因为调数值频繁改动。

### 12.2 技能树规则通用

`needNodes` 和 `conflictNodes` 让每个节点自己描述依赖关系。代码不关心具体树形结构，这对 UI 技能树非常重要。

### 12.3 技能槽和技能物体分离

`Skill_Shard` 管理当前升级和冷却，`SkillObject_Shard` 管理场上碎片。这避免了玩家组件直接管理大量临时物体细节。

### 12.4 动画事件处理出手时机

飞剑和回声攻击都通过 Animation Event 接入实际生成/伤害，动作表现和代码结果更同步。

### 12.5 技能接入属性和元素系统

`SkillObject_Base` 使用玩家 `Entity_Stats` 和 `DamageScaleData` 结算伤害，技能自然吃装备、属性和元素效果。

## 13. 当前实现的风险和优化建议

### 13.1 洗点没有同步清空运行时技能槽

现象：

- `Player_SkillManager.WashAllSkills()` 有实现：`Assets/Scripts/Player/Player_SkillManager.cs:47`
- 但 `RefundAllSkills()` 没有调用它：`Assets/Scripts/UI/SkillTreeUI/UI_SkillTree.cs:37`

风险：

UI 节点退点了，但玩家身上的 `Skill_Base.upgradeType` 可能还保留旧技能。

建议：

`UI_SkillTree.RefundAllSkills()` 末尾调用 `skillManager.WashAllSkills()`，然后重新应用默认技能节点。

### 13.2 `SkillObject_Base.Awake()` 里调试访问 `damageScaleData`

`SkillObject_Base.Awake()` 打印 `damageScaleData.burnDuration`：`Assets/Scripts/SkillSystem/SkillObject_Base.cs:22`

风险：

如果 prefab 上没有提前序列化 `damageScaleData`，而是等 `SetupSword()` / `SetupEcho()` 后才注入，就有空引用风险。更合理的是删除这些 Debug，或在 `Setup*()` 后再打印。

### 13.3 `SkillObject_Shard` 定义了 private Awake，没有调用 base Awake

`SkillObject_Shard` 有自己的 `private void Awake()`：`Assets/Scripts/SkillSystem/SkillObject_Shard.cs:13`

它没有调用 `base.Awake()`，所以基类缓存的 `rb`、`anim` 不会初始化。当前碎片没有用到 `rb` 和 `anim`，所以不一定出 bug，但这是一个隐藏不一致点。

建议：

改成：

```csharp
protected override void Awake()
{
    base.Awake();
}
```

并移除依赖未注入数据的 Debug。

### 13.4 SkillUpgradeType 资产数字依赖 enum 顺序

Unity asset 里保存的是 enum 数字，例如 `upgradeType: 11` 代表 `SwordThrow`。如果在 enum 中间插入新值，旧资产可能全部错位。

建议：

给 enum 显式赋值，或只在末尾追加新类型。

### 13.5 技能分支继续增加后，Skill_* 会变胖

现在 `Skill_Shard.TryUseSkill()` 里有五个分支，规模还可控。如果未来每个技能大类有十几个分支，可以考虑策略模式：

```text
Skill_Shard
  -> IShardUpgradeBehavior
      -> RegularShardBehavior
      -> MovingShardBehavior
      -> TeleportShardBehavior
```

不过现在课程项目用 if 分支更容易学习，不必过早抽象。

## 14. 如何迁移到自己的项目

如果你想把这套技能系统搬到自己的 Unity RPG，可以按这个顺序：

1. 先做 `SkillType` 和 `SkillUpgradeType`，区分“技能大类”和“升级版本”。
2. 做 `Skill_DataSO`，把 UI 展示数据和运行时升级数据放进去。
3. 做 `Skill_Base`，至少包含 `skillType`、`upgradeType`、`cooldown`、`lastTimeUsed`、`CanUseSkill()`、`SetSkillUpgrade()`。
4. 做 `Player_SkillManager`，缓存所有技能，并提供 `GetSkillByType()`。
5. 做技能树节点，节点只负责前置、互斥、技能点、解锁后注入 SO。
6. 做 `SkillObject_Base`，统一处理技能物体的范围检测和伤害。
7. 每个复杂技能都拆成 `Skill_*` 管理器和 `SkillObject_*` 场上物体。
8. 最后再接存档，分别保存技能树 UI 状态和运行时升级类型。

迁移时最容易漏的 Unity 配置：

- Player prefab 上必须挂 `Player_SkillManager` 和各个 `Skill_*` 子组件。
- 每个 `Skill_*` 的 prefab 引用要拖好。
- 技能树节点的 `skillData`、`needNodes`、`conflictNodes` 要配置。
- `UI_SkillSlot.skillType` 要和技能大类一致，否则图标/冷却会更新错槽。
- SkillObject prefab 的 Collider、Rigidbody2D、LayerMask、targetCheck、checkRadius 要配置。
- 动画事件方法名必须和脚本私有方法名一致，例如 `ThrowSword`、`AttackTrigger`、`TryTerminate`。

## 15. 总结

这个项目的技能系统最值得学习的不是某一个技能怎么写，而是它的分层：

```text
SO 数据
  -> UI 技能树解锁
  -> Skill_Base 运行时技能槽
  -> PlayerState / 输入触发
  -> SkillObject prefab 场上表现
  -> 属性 / 伤害 / 状态系统结算
  -> UI 冷却和存档回写
```

它是一套很典型的 Unity 课程项目架构：不追求完全数据驱动或复杂框架，但已经把“配置、解锁、释放、表现、结算、存档”拆到了能扩展、能讲清楚、也能调试的程度。

如果只记一个设计点，就是：

**技能树不释放技能，技能树只改变玩家当前技能槽的升级类型；真正释放时，由状态机/输入触发技能槽，再生成对应的场上技能物体。**

# 脏标记（Dirty Flag）模式深度分析

## 1. 系统定位：解决什么问题？

脏标记不是独立系统，它是 **Stat 属性系统内部的一个缓存策略**，负责解决"属性值被频繁读取但很少被修改"场景下的性能浪费。

**它在项目中的位置：**

```
Stat.cs (数据层)
  ├── baseValue          ← 基础值
  ├── modifiers[]        ← 修饰器列表（装备/Buff）
  ├── needToCaculate     ← ★ 脏标记（本分析的主角）
  ├── finalValue         ← ★ 缓存的计算结果
  ├── GetValue()         ← 读了 99.9% 走缓存，0.1% 触发重算
  ├── AddModifier()      ← 改数据 + 置脏
  └── RemoveModifier()   ← 改数据 + 置脏
```

**如果没有脏标记会怎样？**

每次 `GetValue()` 都要遍历 modifiers 列表求和。看实际调用量——以一次完整的玩家 vs 敌人攻防交换为例：

```
【玩家攻击阶段】
GetPhyiscalDamage() → damage.GetValue() + strength.GetValue()
                    + critChance.GetValue() + critPower.GetValue()      = 4 次 GetValue
GetElementDamage()  → fire.GetValue() + ice.GetValue()
                    + lightning.GetValue() + intelligence.GetValue()    = 4 次 GetValue

【敌人受伤阶段】
GetArmorReduction()      → armorReduction.GetValue()                   = 1 次
GetArmorMitigation()     → armor.GetValue() + vitality.GetValue()      = 2 次
GetElementalResistance() → res.GetValue() + intelligence.GetValue()    = 2 次
GetEvasion()             → evasion.GetValue() + agility.GetValue()     = 2 次
isHeavyDamage()          → GetMaxHealth()→ maxHealth.GetValue()+vit    = 2 次

一次攻防交换 = 17 次 GetValue() × 遍历 N 个 modifier
```

后期角色可能有 8 件装备 + 3 个 Buff + 天赋被动 = **13+ 个 modifier**。战斗中加上 UI 刷新（`UI_StatSlot.UpdateStatValue()` 一次读 15+ 个属性）、生命回复每秒 tick（`RegenerateHealth()` 读 `healthRegen.GetValue()`）、攻击速度同步（`EntityState.SyncAttackSpeed()` 读 `attackSpeed.GetValue()`），**每秒轻松 50-100 次 GetValue() 调用**。

没有脏标记：每秒 100 次 × 13 次循环 = **1300 次无意义的遍历**。而 modifiers 在实际战斗中可能**几秒到几分钟才变一次**。

**初学者通常会怎么实现？**

```csharp
// 反面：新手直接写 —— 每次读都遍历
public class Stat
{
    public float baseValue;
    public List<StatModifier> modifiers;

    public float GetValue()
    {
        float sum = baseValue;
        foreach (var m in modifiers)   // 不管有没有变化，每次都遍历
            sum += m.value;
        return sum;
    }
}
```

看着没问题，甚至跑起来也没报错。但当项目大了、modifier 多了、调用频率上去了，就变成了"温水煮青蛙"式的性能退化。

## 2. 设计思路：为什么这样设计？

### 2.1 核心决策：用空间换时间，用惰性计算替代即时计算

有四种可选方案：

| 方案 | 读性能 | 写性能 | 实现复杂度 | 适用场景 |
|------|--------|--------|-----------|---------|
| **A. 每次重算** | O(n) 慢 | O(1) 快 | 最简单 | modifier 极少（<3）或读极少 |
| **B. 脏标记缓存** | O(1) 快 | O(1) 快 | 简单 | 读多写少（本项目选这个） |
| C. 响应式推送 | O(1) 快 | O(n) 慢 | 中等 | 需要 UI 自动刷新 |
| D. 帧末批处理 | O(1) 快 | O(1) 快 | 复杂 | 一帧内大量写 + 大量读交替 |

项目选了 **方案 B**。原因：

- `读:写 ≈ 1000:1`——方案 A 完全不可接受
- 项目不需要 UI 自动刷新（手动 `TriggerUpdateUI()`）——方案 C 过度设计
- 同一帧内不会出现"写→读→写→读"交替（装备更换在静止时，战斗在运动时）——方案 D 用不上

**这个决策的代价是：** 多了一个 bool 和一个 float 的内存（8 字节），以及每次写操作多一行 `needToCaculate = true`。几乎为零。

### 2.2 为什么缓存放在 Stat 层而不是 Entity_Stats 层？

看 `Entity_Stats.cs` 的复合计算：

```csharp
// Entity_Stats.cs:125
public float GetBaseDamage() => offense.damage.GetValue() + major.strength.GetValue();
```

`GetBaseDamage()` 自己没有缓存。每次调用都重新加两个数。但这个"加法"的成本可以忽略——因为 `damage.GetValue()` 和 `strength.GetValue()` 各自都走脏标记缓存，返回的是**已经算好的 float**。两个 float 相加是纳秒级的。

这是个聪明的**单层缓存**策略——只在数据源头（叶子节点 Stat）做缓存，上层聚合方法只做简单算术。如果 `GetBaseDamage()` 也加脏标记，反而要处理依赖同步问题："damage 变了的时候，谁去标记 GetBaseDamage 的缓存失效？"——引入了不必要的复杂度。

**推演：什么时候才需要在 Entity_Stats 层加缓存？**

如果将来伤害公式变成 `damage^(1.5) * log(strength) * 查表(level)` 这种重计算，那么在 `GetBaseDamage()` 层加缓存才有意义。当前项目全是一阶线性公式（加法+乘法），完全不需要。

## 6. 关键实现细节

### 6.1 初始化——为什么 `needToCaculate` 默认值是 `true`？

```csharp
// Stat.cs:11
private bool needToCaculate = true;
```

Stat 通过 `[SerializeField]` 序列化 `baseValue`。Unity 反序列化时不会调用构造函数，所以 `finalValue` 保持默认值 `0f`。如果 `needToCaculate` 初始是 `false`，第一次 `GetValue()` 直接返回 0，而不是正确的 `baseValue + modifiers`。

初始 `true` 保证**第一次读一定触发全量计算**，这是一个防御性设计——你可以完全忘记"初始化"这回事，读写流程自动收敛到正确状态。

### 6.2 封装——`finalValue` 为什么是 private？

```csharp
// Stat.cs:12
private float finalValue;      // 外界看不到
private bool needToCaculate;   // 外界也看不到
```

所有外部修改必须通过 `AddModifier` / `RemoveModifier` / `SetBaseValue`。这三个方法中，前两个自动置脏，第三个……**没有置脏**。

这是脏标记模式最关键也最容易出错的地方——**新增修改入口时忘了同步置脏**。看代码：

```csharp
// Stat.cs:28-38 — 这两个方法是正确的
public void AddModifier(float value, string source)
{
    modifiers.Add(new StatModifier(value, source));
    needToCaculate = true;    // ✅ 自动置脏
}

public void RemoveModifier(string source)
{
    modifiers.RemoveAll(modifier => modifier.source == source);
    needToCaculate = true;    // ✅ 自动置脏
}

// Stat.cs:50 — 这个方法漏了！
public void SetBaseValue(float value) => baseValue = value;  // ⚠ 没置脏！
```

### 6.3 一个真实的 Bug——`SetBaseValue` 漏了置脏

看 `SetBaseValue` 的调用场景：

```csharp
// Entity_Stats.cs:18-39 — AdjustStatSetup 用于敌人难度缩放
public void AdjustStatSetup(..., float penalty, float increase)
{
    offense.damage.SetBaseValue(offenseGroup.damage.GetValue() * increase);
    //                        ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
    //                        先读了 GetValue()（此时缓存被刷新，needToCaculate = false）
    //                        然后 SetBaseValue 改了 baseValue
    //                        但 needToCaculate 还是 false！
    //                        下一次 GetValue() 返回的是旧的 finalValue！
    defense.armor.SetBaseValue(defenseGroup.armor.GetValue() * penalty);
    // ... 同样的问题
}
```

**为什么这个 bug 当前没暴露？**

推测原因是 `AdjustStatSetup` 在敌人初始化阶段调用，此时还没有任何 modifier 添加（`baseValue` 就是 `finalValue`），且紧接着就会进入战斗触发各种 `GetValue()` 调用，但由于 `baseValue` 恰好和之前一样（初始化后没变过），所以缓存值恰好也是正确的。

但这是**巧合正确**，不是设计正确。一旦调用顺序变成：加 modifier → 读（缓存建立）→ AdjustStatSetup（改 baseValue 但不清缓存）→ 再读（返回旧缓存），bug 就会触发。

**修复只需一行：**

```csharp
public void SetBaseValue(float value)
{
    baseValue = value;
    needToCaculate = true;   // ← 加上这一行
}
```

这个 bug 完美诠释了脏标记模式的**核心风险**：正确性依赖"所有修改路径都记得置脏"这个不变量。一旦有人忘了，不会有编译错误、不会有运行时异常，只有**静默的数值错误**。

### 6.4 `GetFinalValue()` 的局部变量遮蔽

```csharp
// Stat.cs:40-48
private float finalValue;  // ← 字段

private float GetFinalValue()
{
    float finalValue = baseValue;  // ← 局部变量，和字段同名
    foreach(var modifier in modifiers)
    {
        finalValue += modifier.value;  // 编译器正确解析为局部变量
    }
    return finalValue;
}
```

不算 bug（C# 规范明确局部变量优先），但容易让阅读者困惑。建议改为 `float result = baseValue`。

### 6.5 `GetFinalValue()` 没有用 LINQ 的 `.Sum()`

```csharp
// 项目实际写法 —— foreach 遍历
private float GetFinalValue()
{
    float finalValue = baseValue;
    foreach(var modifier in modifiers)
        finalValue += modifier.value;
    return finalValue;
}

// 如果用 LINQ 一行就够
private float GetFinalValue() => baseValue + modifiers.Sum(m => m.value);
```

选择 foreach 而不是 LINQ 的原因：LINQ 会分配迭代器（GC Alloc），而 foreach 在 `List<T>` 上编译器会用 `Enumerator` 结构体（无堆分配）。对于一个战斗中会被周期性调用的方法，避免 GC 是有意义的——尽管脏标记大幅减少了这个方法的调用频率，但这个习惯本身就是好的。

## 7. 优化手段

### 7.1 脏标记的性能收益量化

```
假设：后期角色 13 个 modifier，战斗中每秒 80 次 GetValue()

无脏标记：80 × 13 = 1040 次加法 + 1040 次列表遍历 = 约 0.5ms/秒 的纯浪费
有脏标记：80 × 1 次 bool 判断 ≈ 0.0001ms/秒
收益：约 5000 倍（读路径），且 modifier 越多收益越大
```

实际的 0.5ms 不算什么——但这是**每个角色**。6 个敌人 + 玩家 = 3.5ms/秒。在移动端或低端 PC 上，这已经从"可忽略"变成"值得关注"了。脏标记把这个开销直接归零。

### 7.2 懒计算——不只在时间维度的优化

除了"不重算直到被读"之外，还有一层优化："不算直到真的有 modifier"。如果角色没有任何装备和 Buff（modifiers 为空），`GetFinalValue()` 就是 `return baseValue`——相当于只做了一次赋值，没有遍历。

这说明脏标记的收益和 modifier 数量成正比——modifier 越多，脏标记越有价值。对于前期角色（0-2 件装备），收益微乎其微；对于后期满装角色，收益显著。

## 8. 与 Unity 自带系统的关系

Unity 没有内置的脏标记机制。最接近的是：

- **`[SerializeField]` + `OnValidate()`** — 仅在 Inspector 值改变时触发，运行时无效
- **`ISerializationCallbackReceiver`** — 仅在序列化/反序列化时触发
- **`ScriptableObject` 的 `OnEnable/OnDisable`** — 生命周期钩子，不是数据变更通知

所以这个脏标记完全是项目自己写的。对比同类型的商业方案：

| 方案 | 复杂度 | 适用 Unity 版本 | 本项目选择 |
|------|--------|----------------|-----------|
| 手写 bool 脏标记 | 极低 | 全版本 | ✅ 选这个 |
| UniRx / ReactiveProperty | 中 | 需引入第三方库 | 不选（太重） |
| Unity ECS / DOTS 的 ComponentData | 高 | 需 DOTS | 不适用 |
| ScriptableObject + 事件 | 中 | 全版本 | 过度设计 |

这个选择很务实——一个 bool + 一个 float + 5 行代码，不依赖任何外部库，够用就好。

## 9. 正面例子 vs 反面例子

### 反面：每帧轮询 + 每次遍历

```csharp
// 反面：新手常见写法——Update 中每帧读属性，GetValue 每次遍历
public class UI_StatPanel : MonoBehaviour
{
    public Stat damageStat;  // 直接引用

    void Update()
    {
        // 每帧都跑！damage 可能一小时没变了
        damageText.text = damageStat.GetValue().ToString();
        //                                ^^^^^^^^
        //              每次 GetValue() 都遍历 13 个 modifier
    }
}
```

问题：
1. `Update()` 每帧都读——哪怕属性几天没变过
2. `GetValue()` 每次都遍历——没有缓存
3. 两个问题叠加：每帧 × 每次遍历 = 纯浪费

### 正面：项目的实际做法

```csharp
// Stat.cs:14-23 — 读路径：脏标记守卫，O(1) 命中
public float GetValue()
{
    if (needToCaculate)              // 99.9% 直接跳过
    {
        finalValue = GetFinalValue(); // 只在数据真变了才进
        needToCaculate = false;
    }
    return finalValue;
}

// UI_StatSlot.cs:38 — UI 不是每帧轮询，是事件驱动刷新
public void UpdateStatValue()         // 在 TriggerUpdateUI() 事件链中调用
{
    Stat statToUpdate = playerStats.GetStatByType(statSlotType);
    // ... switch 读值 ...
}

// Inventory_Player.cs:80 — 只有在装备变化时才触发 UI 刷新
private void EquipItem(...)
{
    // ... 加 modifier ...
    TriggerUpdateUI();   // ← 事件驱动，不是每帧轮询
}
```

对比总结：

| 维度 | 反面写法 | 项目写法 |
|------|---------|---------|
| GetValue 实现 | 每次遍历 O(n) | 脏标记缓存 O(1) |
| UI 刷新方式 | Update 每帧轮询 | 事件驱动，数据变才刷 |
| 两者配合 | 帧帧穿透伤害 | 只在装备/Buff 变时才有计算开销 |

## 10. 易混淆点 FAQ

**Q1: `needToCaculate` 和 `finalValue` 为什么都是 private？**

防止外界直接修改。如果 `finalValue` 是 public，可能会有人写 `stat.finalValue = 999f`，然后缓存和真实数据就永久不一致了。private + 只读的 `GetValue()` 强制所有修改走 `AddModifier`/`RemoveModifier`/`SetBaseValue` 三个入口。

**Q2: 为什么不把 `needToCaculate` 做成属性（property）自动触发？**

C# 的属性 setter 可以做到：

```csharp
private bool needToCaculate;
private bool NeedToCaculate
{
    get => needToCaculate;
    set
    {
        needToCaculate = value;
        if (value) finalValue = GetFinalValue(); // 自动计算
    }
}
```

但这样每次置脏都会立即计算，失去了懒计算的收益（连续 5 件装备换装会触发 5 次计算而不是 1 次）。当前的手动检查 + 懒计算的组合更合理。

**Q3: 为什么只有一个 bool 而不是"每个 modifier 一个 dirty"？**

即所谓的"增量更新"——如果只加了 1 个 modifier，为什么还要重新遍历全部？因为 modifiers 是**纯加法叠加**，最终值不依赖 modifier 的顺序。一个 modifier 改变后，旧缓存完全无效，无法做增量修正。除非 modifiers 之间是独立的（比如乘法 modifier），才值得做更细粒度的缓存。

**Q4: 如果有 100 个 modifier，遍历一次会慢吗？会。有什么优化？**

100 个 modifier 遍历一次大概 0.0001ms（现代 CPU 上），战斗中每秒触发一次完全可接受。真的需要优化时可以用**增量维护**——`AddModifier` 时直接 `finalValue += value` 并置 `needToCaculate = false`，`RemoveModifier` 时找到对应的 modifier 值并 `finalValue -= value`。但代价是 remove 时需要能找到对应的 modifier 值（目前 remove 是按 source 匹配，没有直接记录 value），以及 `GetFinalValue` 的"真实来源"丢失了（如果缓存和实际不一致，没有回退机制）。**对于当前项目的规模，不值得。**

**Q5: `SetBaseValue` 到底是不是 bug？**

是。`SetBaseValue` 改了 `baseValue` 但没有置 `needToCaculate = true`。当前没暴露是因为调用时序恰好避开了——`ApplyDefaultStatSetup` 在 `needToCaculate` 初始值 `true` 时调用，`AdjustStatSetup` 后续没有紧接着的 `GetValue` 调用。但这是一个**等待正确时序触发**的 bug，修起来只要一行代码。

**Q6: 脏标记和"响应式绑定"（如 BindableProperty）有什么区别？**

- 脏标记：**拉模式（Pull）**。数据变了只标记，消费者（如 `GetPhyiscalDamage`）自己决定什么时候来读。
- 响应式绑定：**推模式（Push）**。数据变了主动通知所有订阅者，UI 自动刷新。

脏标记更适合**高频读、容忍读到"稍旧"值**的场景（战斗计算）；响应式更适合**需要实时同步**的场景（UI 显示）。当前项目把两者分开了——Stat 用脏标记、Health 用 event（`OnHealthUpdate`）通知 UI。这个分离很合理。

**Q7: 为什么 `GetFinalValue()` 不直接用 `modifiers.Sum(m => m.value)`？**

LINQ 的 `Sum()` 会分配迭代器（堆分配），foreach 在 `List<T>` 上编译器生成结构体枚举器（零堆分配）。虽然脏标记让 `GetFinalValue()` 调用频率很低，但编辑器内切换装备、热重载等场景下还是会被调，避免 GC 是个好习惯。

## 11. 扩展方向

### 扩展一：修复 SetBaseValue（最低成本）

```csharp
// Stat.cs:50 — 当前
public void SetBaseValue(float value) => baseValue = value;

// 修复后
public void SetBaseValue(float value)
{
    baseValue = value;
    needToCaculate = true;
}
```

### 扩展二：脏传播——依赖链缓存

当前项目已经有了隐式的属性依赖：

```
strength    → GetBaseDamage(), GetCritPower()
agility     → GetCritChance(), GetEvasion()
intelligence → GetElementDamage(), GetElementalResistance()
vitality    → GetMaxHealth(), GetBaseArmor()
```

如果未来公式变复杂（比如引入天赋/被动提供的计算系数），可以在 `Entity_Stats` 层也加缓存：

```csharp
private float cachedBaseDamage;
private bool baseDamageDirty = true;

void Awake()
{
    // 订阅底层 Stat 的变更
    offense.damage.OnChanged += () => baseDamageDirty = true;
    major.strength.OnChanged += () => baseDamageDirty = true;
}

public float GetBaseDamage()
{
    if (baseDamageDirty)
    {
        cachedBaseDamage = offense.damage.GetValue() + major.strength.GetValue();
        baseDamageDirty = false;
    }
    return cachedBaseDamage;
}
```

**当前项目不需要——** 20 个属性、一层依赖、线性公式，Stat 层缓存足够。但理解这个扩展方向，当项目规模增长时你就知道该往哪走。

### 扩展三：脏标记 + 合并事件通知

如果 UI 面板增多（装备对比、伤害预测、属性详情），手动 `TriggerUpdateUI()` 会变脆弱。可以给 Stat 加变更事件 + 帧末合并通知：

```csharp
public class Stat
{
    public event Action<Stat> OnValueChanged;

    public void AddModifier(float value, string source)
    {
        modifiers.Add(new StatModifier(value, source));
        needToCaculate = true;
        OnValueChanged?.Invoke(this);
    }
}
```

**但要防"事件风暴"——** 一帧内 5 件装备各改 4 个属性 = 20 次事件。需要合并机制：

```csharp
// 合并版：帧末统一通知
private static HashSet<Stat> dirtyStatsThisFrame = new();

public void AddModifier(float value, string source)
{
    modifiers.Add(new StatModifier(value, source));
    needToCaculate = true;
    dirtyStatsThisFrame.Add(this);
}

// 在 LateUpdate 或协程 WaitForEndOfFrame 中
public static void FlushDirtyStats()
{
    foreach (var stat in dirtyStatsThisFrame)
        stat.OnValueChanged?.Invoke(stat);
    dirtyStatsThisFrame.Clear();
}
```

### 扩展四：版本号替代 bool（帧同步场景）

用 `int version` 替代 `bool`：

```csharp
private int version = 0;
private int cachedVersion = -1;
private float finalValue;

public float GetValue()
{
    if (version != cachedVersion)
    {
        finalValue = GetFinalValue();
        cachedVersion = version;
    }
    return finalValue;
}
```

好处：版本号可暴露给外部系统——"上次我读的是 v3，现在 v5 了，要重新处理"。适合帧同步（判断属性是否在两次快照间变化）或 undo/redo 系统。当前项目不需要。

### 扩展五：条件性置脏

```csharp
public void AddModifier(float value, string source)
{
    if (Mathf.Approximately(value, 0)) return;  // 零值不添加
    modifiers.Add(new StatModifier(value, source));
    needToCaculate = true;
}
```

避免 value=0 的无意义 modifier 触发缓存失效。但要谨慎——0 值 modifier 有时是故意留的（"预留后续升级"），砍掉可能影响设计意图。

## 12. 总结

**脏标记模式的本质：用一个 bool（8 比特），把 O(n) 的遍历从"每次读"推迟到"数据真的变了的第一次读"。前提是读远多于写。**

这个项目做得好的：
- 极简实现——5 行代码，没有引入任何抽象
- 封装强制正确——`finalValue` private，修改入口自动置脏
- 初始值兜底——`needToCaculate = true` 保证反序列化后第一次读正确
- 单层缓存——只在 Stat 叶子节点做缓存，上层复合方法不做

需要注意的：
- **`SetBaseValue` 漏了置脏**——这是脏标记模式最常见的陷阱：新增修改入口忘了同步。修起来一行代码
- `GetFinalValue()` 局部变量和字段同名——维护性小问题

扩展方向上，**脏传播（依赖跟踪）**是最自然的下一步——当 `strength` 变了，自动标记 `GetBaseDamage()` 缓存失效。但要等到公式足够重、依赖足够深才值得做。目前项目保持简单是正确的选择。

**最该学到的：脏标记不是一个"复杂模式"，它是一行代码（`needToCaculate = true`）的纪律。真正难的不是实现它，而是在所有修改路径上都记得调用它。封装（private 字段 + 有限入口方法）是保证这个纪律的手段。**
